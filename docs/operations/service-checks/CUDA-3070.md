# RTX 3070 (CUDA) worker

PandoSI can add an NVIDIA GPU as another HTTP stem without changing the
root protocol. The worker uses `onnxruntime-gpu`; the existing Intel CPU,
iGPU, and NPU workers remain on their original runtimes.

## Environment

Use a separate environment because `onnxruntime` and `onnxruntime-gpu`
provide the same import name:

```bash
python -m venv --system-site-packages .venv-cuda
.venv-cuda/Scripts/pip install onnxruntime-gpu==1.31.0
nvidia-smi
```

Verify the provider before starting a worker:

```bash
.venv-cuda/Scripts/python -c \
  "import onnxruntime as ort; print(ort.get_available_providers())"
```

Expected:

```text
['TensorrtExecutionProvider', 'CUDAExecutionProvider',
 'CPUExecutionProvider']
```

## Run a CUDA stem

```bash
.venv-cuda/Scripts/python -m pando.worker \
  --node-id nvidia-3070-cuda \
  --root http://ROOT_IP:8080 \
  --pairing-token-file ~/.pando/stem-pairing.token \
  --backend onnx \
  --onnx-path artifacts/laya-en-fixed.onnx \
  --device CUDA
```

The backend refuses to start if the first provider is not
`CUDAExecutionProvider`, so a misconfigured machine cannot silently
run a CPU worker under a CUDA label.

The graph is still Laya; the difference is the execution backend and
the protocol-level checkpoint identity (`onnx-cuda`).

## Verify live hot-plug

```bash
python tools/hetero_http_check.py --yes --hotplug-cuda
```

This starts the Intel workers first, then joins the CUDA stem into the same
running root quorum.

## Native PyTorch stem (non-OpenVINO ecosystem)

The CUDA stem above uses `onnxruntime-gpu`, which keeps it in the same
inference ecosystem as the Intel workers. To join a worker from a genuinely
different ecosystem, run Laya through native PyTorch in the same
`.venv-cuda` environment:

```bash
.venv-cuda/Scripts/python -m pando.worker \
  --node-id nvidia-3070-torch \
  --root http://ROOT_IP:8080 \
  --pairing-token-file ~/.pando/stem-pairing.token \
  --backend laya \
  --device CUDA
```

This requires `torch` (CUDA build) plus `transformers`; the checkpoint is
resolved through `HF_HOME` (repo `.hf-cache` by default). The stem fails
closed if CUDA is requested but torch cannot see it, and it serializes
inference so one model serves the threaded HTTP handler safely. Its
checkpoint identity is `torch-cuda`, distinct from the `onnx*` group.

Bench it directly, or join the full heterogeneous quorum:

```bash
.venv-cuda/Scripts/python tools/torch_laya_bench.py --device CUDA
python tools/hetero_http_check.py --yes --torch-stem --skip-npu
```

## Real RLCD training

```bash
.venv-cuda/Scripts/pip install torch==2.14.1+cu130 \
  --index-url https://download.pytorch.org/whl/cu130
HF_HOME=D:/PandoSI/.hf-cache \
  .venv-cuda/Scripts/python tools/rlcd_cuda_train.py --json
```

The script trains on `rollouts/train_rlcd.jsonl`, saves a CUDA checkpoint,
and compares original vs trained decisions on the English graft slice.
