# Research Round 67 — Per-stem latency memory and adaptive timeouts

Date: 2026-10-14

## Change

The coordinator now records per-stem execution observations:

- successes and failures;
- last latency;
- EWMA latency;
- last error.

Each `_call_stem` starts with a 5-second discovery timeout. After successful
observations, the next timeout is derived as:

```text
timeout = clamp(EWMA_latency * 4 + 250 ms, 500 ms, 30 s)
```

This keeps the first contact tolerant of cold-start variation, then tightens
the failure budget around each worker's measured distribution.

## Four-runtime measurements

After five decisions in the CPU + CUDA + iGPU + NPU swarm:

| worker | last ms | EWMA ms | derived timeout |
|---|---:|---:|---:|
| Intel CPU ORT | 146.4 | 155.7 | 0.87 s |
| RTX 3070 CUDA | 94.0 | 187.5 | 1.00 s |
| Intel iGPU OpenVINO | 109.1 | 116.3 | 0.72 s |
| Intel NPU OpenVINO | 168.1 | 174.4 | 0.95 s |

The swarm returned four votes in every decision. Wire p50 was 214.2 ms and
root fan-out p50 was 195.2 ms in this run, within normal variance of the
round-66 parallel result (226.3 ms fan-out).

## Why this matters

Before this change, a stem that accepted TCP but never returned a vote could
hold the quorum for the global 30-second timeout. The observed local budgets
are now 0.72–1.00 seconds, so an unresponsive worker is isolated roughly
30–40x faster while the remaining quorum still answers.

This is a robustness change, not a claimed latency optimization: the
successful four-worker path still waits for all responding stems.

## Evidence

- `node_stats` is exposed through `/nodes` for local operators.
- `test_stem_timeout_adapts_to_observed_latency` proves the second call uses
  a learned timeout smaller than the initial 5-second budget.
- the existing parallel fan-out test still verifies overlapping calls.
