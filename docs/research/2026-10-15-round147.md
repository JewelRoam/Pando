# Research Round 147 — The cross-device path, verified on one machine

Date: 2026-10-15

## What was actually blocked

Every measurement this session ran on loopback, and the objective's second
clause - 从单设备内多算力单元到跨设备集群 - has been reported as blocked by
hardware since round 124: there is no WSL, no Docker and no second machine
here. But "no second machine" and "no second network path" are different
claims, and only the first is true. The LAN code path - the grant gate, the
binding, the advertisement, discovery, and HTTP over the machine's real
interface - had never been exercised at all.

`tools/lan_path_check.py` exercises it. A probe first established that the
host can reach itself on its LAN address (`192.168.31.100` -> 200), so
Windows' firewall is not silently blocking the path this check depends on.

## Three properties, none of them loopback

| what | result |
|---|---|
| the operator's grant | `grant lan_listen --resource 0.0.0.0:<port>` -> exit 0, recorded in the ledger |
| discovery | a second `pandosi join --lan` process, told **no URL**, reports `found existing root at http://192.168.31.100:56385` |
| the fleet | `members registered with the root: 2` |
| a decision over the network | `tier=auto responded=2 quorum=2 votes=['onnx','onnx']` |

So the cross-device software path works end to end on a real interface. What
is missing for a genuine two-device fleet is the second device and nothing
else: no code path is untested between here and a TV box on the same LAN.

## What the check learned about the product, not the code

The first two runs failed in ways worth recording, because both are the
*designed* behaviour:

**Discovery finds the address; the token authorises joining.** The second
process discovered the root on its own and then refused to register: `root
http://192.168.31.100:56385 requires --pairing-token`. An operator reads the
token off the root's console (`stem pairing token: ...`) and hands it to each
device - which is what pairing a device to a swarm should be, and what the
check now does.

**A device has to load its model before it can vote.** Two runs asked for a
decision while the stems were still loading 570 MB of int8 weights and got an
escalate with no quorum; the fix was to poll the root's own `/status` for its
member count instead of guessing a delay. That is a check-harness lesson, not
a system one, but it is the same lesson as round 126: patience belongs in the
harness, and the system should be asked what state it is in.

## Where the objective stands

| clause | state |
|---|---|
| 弹性扩缩容 | measured live: capacity from units (host-capped), quality from opinions, removal free |
| 异构软硬件融合 | three execution units answering identically, scheduled by host cost, **and now a second process joining over the LAN interface** |

The remaining gap to a real cross-device fleet is one physical device.
