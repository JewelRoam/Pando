# Research Round 106 — Batched spore transfer: 1.68 GB in 14 seconds

Date: 2026-10-14

## The problem

Round 105 got self-replication working end to end and immediately showed its
cost: the 1.68 GB artifact took roughly four minutes to replicate, because
`pull_spore` issued **one HTTP request per 64 KiB chunk** - about 26,000
requests, each on a fresh connection. That is not a usable rate for a system
whose premise is reproducing onto whatever device is at hand.

## The change

A batched endpoint on both spore servers plus a keep-alive client:

```text
GET /spore/chunks/<name>/<start>/<count>  -> concatenated chunk bytes
```

- `SporeServer` and `rootd` serve it; the single-chunk route stays for
  selective re-fetch.
- `pull_spore(batch_chunks=64)` fetches batches over **one** `HTTPConnection`
  instead of a new socket per request.
- **Verification is unchanged**: every chunk is still hashed against the
  manifest before it is written. A chunk that fails inside a batch falls back
  to the per-chunk path with the existing three-attempt rule, so a transient
  fault costs one request rather than the file.
- `batch_chunks=1` reproduces the old request-per-chunk behaviour, which is
  what makes the comparison below a controlled A/B on identical bytes.

## Measurements

`tools/spore_transfer_check.py`, same payload, both paths, byte-identical
results checked with `artifact_digest`:

| payload | per-chunk | batched | speedup |
|---|---:|---:|---:|
| synthetic 48 MB (768 chunks) | 3.44 s (13.9 MB/s) | **0.42 s (113.4 MB/s)** | 8.2x |
| real artifact 1.68 GB (25,768 chunks, graph + weight blob) | ~125 s | **14.24 s (113.1 MB/s)** | **8.8x** |

End to end, `tools/reproduce_check.py` - which transfers, attest, admits, and
registers a real joiner - went from about **4.5 minutes to 59 seconds**. The
transfer leg improved 8.8x; the remainder is now dominated by the child
loading a 1.7 GB graph, not by moving it.

The batched rate is ~113 MB/s on loopback, which is close to what this
per-chunk-hashing Python path can do; the real limit for a remote device is
the link, not the request count any more.

## A measurement bug worth recording

The first version of the transfer tool "measured" `artifacts/laya-en.onnx`
and reported a 6.2x speedup over 53 chunks. It was serving **only the named
file** - a 3 MB protobuf - while the weights are the 1.68 GB `.data` sibling.
It measured a graph, not an artifact.

That is the same defect class as round 103's digest and round 94's
node-count split: a plausible number computed on the wrong set. Fixed by
serving `artifact_files(payload)` and comparing with `artifact_digest`, which
is exactly what a root serving `--serve-spore` now does.

## Test coverage

`test_batched_spore_transfer` (in the 16-test smoke suite, so it runs in CI):
a 151-chunk payload crosses several batch boundaries with a short final
chunk and comes back byte-identical; then a transient corruption is injected
into the first batch response and the pull must still succeed via the
per-chunk fallback. The spore chain, root surface, DAG and reproduction
checks all re-ran green.

## Open

- Batching reduces *how many requests* move a fixed amount of data. It does
  nothing about *how much* data moves; that is the blueprint's Phase 5
  (content-defined chunking with deltas), still unbuilt. For a lineage that
  differs from its parent by a few megabytes, 1.68 GB is still the wrong
  number to send.
- Compression is absent: the graph protobuf compresses well, the weight blob
  less so, and neither is attempted.
- The transfer is still whole-artifact. Resuming an interrupted pull, and
  pulling only the files a replica is missing, are both untouched.
