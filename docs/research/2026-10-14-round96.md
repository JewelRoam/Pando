# Research Round 96 — The topology planner, and why a slow voter is a liability

Date: 2026-10-14

## What was built

`pandosi/topology.py` turns rounds 93-95 from prose into a decision
function, and `tools/topology_check.py` pins it to this project's own
measurements (wired into `ci.yml`).

```text
plan_topology(devices, links, model_gb, activation_mb, quorum=3,
              max_stages=3, min_gain=1.15) -> Plan(mode, reason, ...)
```

`mode` is `replicate`, `stage`, or `infeasible`. The planner:

1. prefers replication, because it needs no assumption about links and never
   makes one device the bottleneck for another (round 93);
2. considers a pipeline only when no single device can hold the model, or
   when a split beats replication by `min_gain` on measured throughput;
3. splits work **in proportion to measured device speed**, so every stage
   finishes at the same time, and checks that each stage's share fits in
   that device's memory and that every hop satisfies `L < T` (rounds 93-94);
4. prices a decision as `latency = max(voter)` and
   `throughput = 1/max(voter)` for replication — every voter must answer the
   same question — and `latency = sum(stage) + sum(link)`,
   `throughput = 1/max(stage)` for a pipeline.

## The result that fell out of writing it down

Feeding round 94's own hardware into the planner exposes something the
experiment obscured. Round 94 split at node 900 — 50/50 **in nodes** between
a 13.7 ms device and a 106 ms device — and measured 0.47x. But the planner
does not split by node count; it splits by speed:

```text
devices : rtx3070 (13.7 ms, 8 GB), intel-cpu (106 ms, 64 GB)
quorum 2, model 2 GB, link 1.2 ms

replicate : latency 106.0 ms, throughput   9.4 req/s   (fast device waits)
stage     : latency  25.5 ms, throughput  82.4 req/s   (8.74x)
            shares rtx3070 0.886 / intel-cpu 0.114, both stages 12.1 ms
```

Eight times the throughput *and* a quarter of the latency, from the same two
devices. The 50/50 cut in round 94 gave the CPU 41.7 ms of work while the GPU
needed 6.7 ms — the opposite of proportional. Round 94's "offloading to a
slower device loses" is therefore only true for a *node-count* split; a
speed-proportional split is a different regime.

**Why this is not a contradiction, and why it matters.** A synchronous
quorum asks every voter the same question. When one voter is 7.7x slower,
the fast device spends most of its time waiting, and — per round 95 — the
slow voter's answer carries no extra information, because the same
checkpoint through a different runtime votes identically. Redundancy across
a slow, same-checkpoint device is pure cost. Giving that device a
proportional slice of the model instead turns the same hardware from a drag
into capacity.

That yields a routing rule the swarm does not have yet:

```text
device is fast, or holds a DIFFERENT checkpoint   -> voter (adds information)
device is slow, same checkpoint                   -> pipeline stage (adds compute)
                                                     or excluded entirely
```

## Honest status of this result

This is a **model-based prediction, not a measurement**. The planner's
numbers come from the estimator above, and the host has one GPU, so the
two-disjoint-GPU and speed-proportional-split cases are unverified here.
What *is* measured is: the interface is small (0.15-1.22 MB), the loopback
hop is 1-2 ms (round 94), a same-CPU split buys nothing (0.95-1.13x), and a
50/50 cross-device split loses (0.47x). The planner's `min_gain=1.15`
threshold and the "or no device holds the model" clause keep it
conservative in exactly the cases that are unverified.

## Next experiment (falsifiable)

Measure the speed-proportional split rather than the 50/50 one: find the cut
where the CPU stage's measured time equals the CUDA stage's measured time
(from the round 94 sweep, somewhere past cut 1350), then compare against
quorum-1 replication on the 3070. The planner predicts the split reaches
~83 req/s against ~73 req/s replicated at 13.7 ms — a modest 1.14x on this
hardware, not the 8.74x above, because the comparison that gives 8.74x is
against a *quorum-2* replication where the slow voter drags. Both
comparisons are worth reporting separately; conflating them would be the
easiest way to overstate this.
