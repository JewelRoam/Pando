# Research Round 93 — Transport-aware topology: replicate vs stage

Date: 2026-10-14

## The question

Given devices we did not choose, connected by links we cannot control, how
should they be "拼凑" into one system? Two topologies were proposed:

- **distant groups** -> data-/agent-parallel: every group runs the whole
  model and only a summary crosses the link;
- **nearby devices** -> pipeline-parallel: split the model into stages and
  stream activations between them.

This round does not add a feature. It fixes the decision rule and checks it
against numbers this project has already measured, so the next
implementation round has a target instead of a vibe.

## The rule

Let `T` be the compute time for one stage of a model split into `S` stages,
and let `L` be the inter-stage link cost (one-way latency plus transfer of
the activation tensor).

```text
pipeline throughput   = 1 / max(T, L)          (steady state)
single-device         = 1 / (S * T)
```

So a pipeline pays off **only while `L < T`**. Once the link is slower than
a stage's compute, throughput collapses to `1 / L` and the split is
strictly worse than not splitting. This is the whole intuition, quantified:

```text
if  rtt + activation_transfer  <  per_stage_compute:
        stage        (pipeline-parallel)
else:
        replicate    (data-/agent-parallel: one summary vote per group)
```

The two are not exclusive. Replication is always safe and always available;
staging is an optimization that must be *earned* by a fast link.

## What we have already measured

| link / unit | measured cost | source |
|---|---:|---|
| on-host loopback fan-out (4 workers) | fan-out p50 177-226 ms, dominated by the slowest worker | rounds 66, 67, 92 |
| LAN interface (`192.168.31.100`) | registers + serves through the real NIC, protocol unchanged | round 68 |
| slow "remote-like" link | healthy 188 ms -> degraded 1500 ms -> skipped in 16.1 ms | round 69 |
| cross-group summary vote | 176.9 ms fan-out, 4/4 responded | round 72 |
| per-stage compute, RTX 3070 forward | 15 ms (ORT CUDA) / 25 ms warm (torch) | rounds 65, 92 |
| per-stage compute, Intel iGPU | 25.6 ms | round 34 |
| per-stage compute, Intel NPU | 95.7 ms | round 54 |

Filling the rule in with these numbers:

| link cost | verdict |
|---|---|
| on-host IPC/loopback, ~0.2-1 ms | pipeline viable even at a 4-way split (stage ~6 ms) |
| same-LAN, ~1-20 ms | pipeline marginal; only for coarse stages |
| slow/remote link, 100 ms-1.5 s | replicate only; a stage boundary here would be a hard stall |
| beyond the learned timeout | the worker is dropped from the quorum and rejoins after cooldown |

The rule says the interesting boundary is **a few milliseconds**, i.e. the
same host or a very fast local fabric. Over any real LAN or WAN, the answer
is the one already implemented: replicate and aggregate summaries.

## What is already built vs missing

Built (replication side):

- elastic membership: join/leave with no handshake, heartbeat TTL 15 s
  (rounds 70, 71);
- transport tolerance: per-stem EWMA timeouts, failure cooldown, quorum
  shrinkage on a slow link (rounds 67, 69);
- hierarchy: `pandosi.bridge` makes a whole remote group look like one
  checkpoint named `group-b`, reusing the plain stem contract (round 72);
- ecosystem independence: any runtime joins by serving `/decide`
  (`docs/STEM-PROTOCOL.md`, round 92).

Missing (pipeline side): a **stage executor**. Concretely:

1. partition the graph. `artifacts/laya-en-fixed.onnx` is one 1.7 GB
   graph; a stage split needs a boundary cut into two graphs whose
   interface is named activation tensors. We already do ONNX surgery in
   `tools/postprocess_onnx.py` (`IsNaN` removal) and `tools/fix_gathernd.py`,
   so the tooling precedent exists;
2. a stage stem: serves `POST /forward` with an activation tensor instead
   of `POST /decide` with a decision — a second, smaller contract;
3. a chain supervisor: routes input to stage 0 and the final activation
   back to a head, and applies the `L < T` test before choosing to stage.

## Why this matters for the goal

The unlimited-reproduction direction needs a topology that degrades
gracefully: the system must always be able to *use* a device it just
acquired, whatever the link. The rule above gives the ordering — replicate
first (always works, no assumptions about the link), stage only when a
measurement proves the link is fast enough. Reproduce-and-aggregate is the
floor; pipeline-parallel is an opportunistic optimization layered on top.

## Next experiment

Cut the Laya encoder graph at the last block, serve the two halves as two
stage stems on one host, and measure `L` (loopback tensor transfer) against
`T` (per-stage forward). If `L < T` holds for a 2-way split, pipeline
latency should fall below the 26 ms single-device forward; if it does not,
the experiment has falsified on-host staging for this model and the note
should say so.

> **Update (Round 94):** the experiment was run. `L < T` does hold, but it
> is necessary and not sufficient — on-stream staging bought no throughput
> on a shared CPU, and offloading half the model to a slower device made
> things 0.47x worse. See `2026-10-14-round94.md` for the corrected rule.
