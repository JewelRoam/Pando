# Research Round 133 — The host is the ceiling, and one host is noisy

Date: 2026-10-15

## The confound round 132 left

Round 132 measured a capacity ceiling on one host - two units added capacity
at k=1 and the third did not - and named a reason that was also a confound:
all three stems ran inside one Python process, sharing a GIL, a scheduler and
an interpreter per request. The shape a fleet actually deploys is separate
`stemd` processes, so the ceiling had to be re-measured that way.

`tools/process_fleet_capacity_check.py` starts three real stem processes
(CPU, Intel iGPU, Intel NPU, each with its own interpreter, session and HTTP
server, heartbeating to a root that is the only shared thing in the picture),
then drives load at a fixed concurrency while units are added and the quorum
size changes.

## What survives the fix

Two findings are stable across every run and every process shape.

**The units do not add capacity on one host.** 160 decisions per cell, four
concurrent clients:

| configuration | throughput | p50 | p95 |
|---|---:|---:|---:|
| 1 unit, k=1 | 26.5 /s | 153 ms | 237 ms |
| 2 units, k=1 | 25.0 /s | 158 ms | 258 ms |
| 3 units, k=1 | 26.0 /s | 156 ms | 241 ms |
| 3 units, k=3 | **9.6 /s** | 383 ms | 689 ms |

Adding the iGPU and the NPU to a CPU stem changes nothing, with or without
separate processes. The bottleneck is not the accelerator count and not the
GIL: it is the host CPU doing the per-request work every stem shares -
tokenisation, JSON, HTTP, the response path - and a single stem already
saturates it at four concurrent clients.

**k costs a factor of two to three.** 3 units at k=1 reach 26.0/s where k=3
reaches 9.6/s, with p50 latency 156 ms against 383 ms. Round 132 measured the
same ratio in-process (24.1 -> 10.5/s) and it reappears here, which is the
strongest evidence in this round: one quantity moved by the rule, the other
by the hardware, and only the rule's effect is reproducible.

## What the accelerators are worth under load

At four concurrent clients, each unit alone, measured in its own process:

| unit | throughput | p50 |
|---|---:|---:|
| CPU | 24.9 /s | 157 ms |
| Intel iGPU | 24.0 /s | 170 ms |
| **Intel NPU** | **33.2 /s** | 112 ms |

This inverts round 131's sequential ordering, where the NPU was the slowest
unit (8.7 decisions/s against the iGPU's 17.6 and the CPU's 10.0). "Fast" is
a property of the load, not of the device: sequentially the NPU pays a fixed
per-request cost, concurrently it is the one stem whose work does not contend
with the host's other cores. Round 110 made quorum picking load-aware on the
strength of a simulated device; here is a real device that changes rank with
concurrency, which is what that rule is for.

## The number that should be trusted least

A single-stem sweep of client concurrency - 1, 2, 4, 8 clients at 40
decisions each - gave 12.9, 19.5, 24.4 and **16.8** decisions per second,
which reads as "peaks at four clients and collapses at eight". A later run of
the same one-unit configuration at eight clients measured **34.1**/s. Same
configuration, same code, same host, twice the throughput.

So single-host capacity numbers carry roughly 30-50% run-to-run variation
here, and any conclusion that depends on a single cell should be treated as
noise. What this round is willing to conclude is limited to the two effects
that reproduced across runs and process shapes (units do not add; k divides
throughput) and to the ordering that is structural rather than numeric (the
host is the shared resource).

## Where capacity actually lives

The project's own arc points the same way: round 109 found that replicas buy
nothing without spreading, round 110 made spreading load-aware, round 121
made a replica one vote, round 129 made a correlated family one vote, and
rounds 132-133 now measure that a second, third and fourth unit on the same
host buy nothing at all. The next doubling is not another unit on this
machine - it is either **another machine** (where the per-request host work is
somebody else's CPU) or **less host work per request** (batching, fewer
layers, a tokenizer that is not Python). Both are concrete; only one of them
is a hardware purchase.
