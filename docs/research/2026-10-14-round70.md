# Research Round 70 — Runtime scale-up and scale-down

Date: 2026-10-14

## Question

Can the swarm change size while root is running, without restarting the
coordinator or changing its token, registry, or quorum code?

## Experiment

`tools/swarm_check.py` now runs three phases with independent OS processes:

1. start root and three stems;
2. make a decision with quorum size 3;
3. start two more stems against the same running root; make a decision with
   quorum size 5;
4. terminate one stem, wait for the 15-second heartbeat expiry, and make a
   decision with quorum size 4.

No root restart or code reload occurs between phases.

## Result

| phase | registered | quorum | responded | tier |
|---|---:|---:|---:|---|
| initial | 3 | 3 | 3 | verify |
| scale-up | 5 | 5 | 5 | auto |
| scale-down after expiry | 4 | 4 | 4 | verify |

The scale-up stems used additional checkpoint identities and were selected
by the existing checkpoint-diversity policy. The scale-down stem disappeared
from `/nodes` after heartbeat expiry and was absent from the next quorum.

## Interpretation

This is direct evidence for the elastic membership contract:

- new workers can join a live root;
- quorum selection automatically expands to the new checkpoint set;
- dead workers expire without a restart;
- decisions continue through every transition;
- no shared runtime, shared device, or process restart is required.

The test uses mock decision backends so the membership behavior is isolated
from model load. Real model workers have already been tested separately in
the CUDA/CPU/iGPU/NPU and network-degradation experiments.

## Limitation

The 15-second heartbeat expiry dominates scale-down time. A production
policy may tune heartbeat TTL by topology, but that should be based on
measured WAN jitter rather than lowered blindly.
