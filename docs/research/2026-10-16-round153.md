# Research Round 153 — The admission rule meets real candidates; the fleet runs with the CPU left alone

Date: 2026-10-16

## Part 1 — the admission rule, applied to what exists

Three rounds built the rule: *independence* (rounds 122-137), *capability*
(round 150), *replication* (round 152). `tools/admit_member_check.py`
applies it to real material: the seated trio (`english`, `multilingual`,
`typed-decisions`) and all five fine-tuned candidates, every one of them
voted on split D — the fourth wording inventory (240 rows) none of them ever
trained on.

| candidate | recipe | accuracy on D | mean phi vs seated | fleet decided seated+it | verdict |
|---|---|---:|---:|---:|---|
| seated trio alone | - | 0.7292 / 0.5958 / 0.7208 | - | 0.8125 | - |
| ft-v3 | 720 rows | 0.9417 | +0.043 | 0.8667 | admit |
| ft-v3-s1 | 720 rows | 0.9125 | +0.222 | 0.8708 | admit |
| ft-v3-s2 | 720 rows | 0.9750 | +0.161 | 0.8792 | admit |
| ft-v4 | 960 rows | 0.8292 | +0.263 | 0.8833 | admit |
| ft-v4-s1 | 960 rows | 0.9625 | +0.085 | 0.8875 | admit |

Floors: capability > best seated + 4 points (0.7292 + 0.04 = 0.7692), mean
phi < 0.6, and the fleet's decided accuracy must not fall.

Three things this makes precise.

**Every candidate clears every floor, and independence is the least
interesting part.** Mean phi runs +0.04 to +0.26 — fine-tuning this lineage
decorrelates rather than copies (round 119's descendant measured +1.000).
Capability clears by 6 to 21 points. But —

**Admission is a floor, not a lift.** `ft-v3-s2` decides 0.9750 alone; with
it seated, the *system* decides 0.8792. Seating a strong member does not
raise what the gate+combiner (fitted on the weaker trio) does with a
four-member quorum. The fleet-decided floor in the rule was written to keep
out saboteurs; it is far too weak a bar for "worth seating" for a system
whose gate is calibrated to its incumbent membership. The honest reading:
the rule admits candidates that *cannot hurt*; whether they *help* is a
question about the gate, not about the member.

**A recipe is judged by its samples' mean, and the 960-row recipe is the
current loser.** Means: 720 rows -> 0.9431, 960 rows -> 0.8959. Every
individual run of both recipes is admitted, including `ft-v4` at 0.8292 —
the worst draw of the noisier recipe, sitting 2.6 points above the
capability floor. Admission of a run to the bench is not selection of a
recipe for the next generation; that decision uses the mean, and at this
corpus size the spread (5.0 / 13.3 points, round 152) dominates the
difference between recipes. The next refinement the rule needs: the recipe's
mean must clear the capability floor before any of its runs is admissible.

## Part 2 — the fleet with no CPU inference at all

Round 133 found the host CPU is the fleet's ceiling; round 134 priced it: a
CPU stem spends ~2.9 CPU-seconds per decision, the iGPU ~36 ms, the NPU
~4 ms. On a personal computer that ranking decides the architecture: the CPU
is the part that is always busy (the browser, the editor, the agent), and
the accelerators sit idle. Round 130 sketched a GPU+NPU fleet with no CPU
stem, but only ever ran the NPU alone.

`tools/cpu_free_fleet_check.py` runs the fleet a daily driver actually has:

- `igpu` — OpenVINO GPU, english lineage;
- `npu` — OpenVINO NPU, english lineage (a same-lineage replica);
- `dgpu` — the RTX 3070, **torch/CUDA, carrying `ft-v3`** — the member the
  project trained itself, and the first live member from outside the
  OpenVINO ecosystem. Same HTTP stem contract, same quorum.

No CPU inference anywhere. Set D (240 rows nothing in the fleet saw), quorum
3 of 3, two full runs:

| | run 1 | run 2 (corrected) |
|---|---:|---:|
| wall | 28.6 s | 33.1 s |
| throughput | 8.39 rows/s | 7.24 rows/s |
| p50 | 112 ms | 119 ms |
| 3-vote answers | 240/240 | 240/240 |
| host CPU before -> during | 0% -> 16% | 0% -> 22% |
| CPU left free | 84% | **78%** |
| igpu CPU/decision | 54.6 ms | 75.5 ms |
| npu CPU/decision | 5.3 ms | 5.1 ms |
| dgpu CPU/decision | *0.00 measured* | **45.0 ms** |
| fleet + root CPU per row | 72.7 ms | 135.6 ms |

Quality, identical in both runs: **auto-executed 200/240 at 0.8500**,
declined 40, advisory suggestions on those at 0.7250 — a decided answer on
199/240 = **0.8292**. Two honest limits on that number: `ft-v3` has no
temperature table, so every one of the 240 rows carries
`uncalibrated_checkpoints: [ft-v3]` — rootd reports this rather than
silently trusting saturated confidences, and it is an acting policy
(`AutonomyLoop`) that refuses to auto-execute on them; this driver counts
the tiers as rootd emits them, so "200 auto rows" is the gate's raw
decision, not yet a deployment-ready one. And the gate+combiner were fitted
on the seated trio — the same "admission is not a lift" tension as Part 1.
Recalibrating the gate for the four-member fleet is the obvious next round,
not a surprise result.

### The measurement that lied, and why it is in this log

Run 1 measured **0.00 CPU-seconds** for a stem that had just served 240
decisions. Cause: a venv's `Scripts\python.exe` is a 255 KB *redirector*
that runs the real interpreter as a child, so the pid `Popen` returns burns
nothing while its grandchild does all the work. Caught because a strong
candidate number that is too good ("the 3070 stem costs the CPU nothing")
deserves skepticism; fixed by walking the process tree
(`CreateToolhelp32Snapshot`). Run 2's two independent channels — the
window-delta tree CPU and the stem's own `/health` self-report — agree to
0.3 ms (45.05 vs 45.38), so 45 ms CPU/decision for a torch/CUDA member is
the number this project will use.

### What this establishes

- A three-accelerator fleet — two ecosystem vendors' runtimes, two
  instruction-set families, one process per device — decides a full
  held-out suite with **zero CPU inference**, leaving 78-84% of the host
  CPU for its owner, at 7-8 rows/s and p50 ~115 ms.
- The torch/CUDA member in the same quorum over the same HTTP contract
  closes the "non-OpenVINO ecosystem" gap: votes from `.venv-cuda` count
  like any others, at 45 ms CPU/decision against the CPU stem's ~2856 ms —
  63x cheaper, on the accelerator that used to be the *optional extra*.
- The cost ranking the root already implements (round 136's cost bands)
  is exactly what a personal machine needs: at k=2 it will prefer
  npu (5 ms) and igpu (55-76 ms) and leave even the discrete GPU asleep;
  the 3070 is woken when the quorum needs what only it carries.
- The remaining CPU cost is coordination, not inference: root + driver
  ~9-10 ms per row on this machine, versus 126 ms of device-side CPU and
  versus a CPU-only stem's ~2856 ms per decision (round 134).
