# Research Round 8 — three-EU benchmark: one success, two precise failures (2026-10-14)

## Setup
- laya-en exported to ONNX: fp32 (3.3MB + 1.6GB data) + ORT-dynamic-int8 (571MB).
- tools/eu_bench.py: captures a REAL input batch via ONNXAgent run-spy
  (input_ids/attention_mask [2,43], marker_pos/marker_mask [2,3], qtype [2]),
  then static-reshapes the OV model and benchmarks per EU.

## Results (Core Ultra 7 255H, openvino 2026.4.1)

| EU | int8 graph | fp32 graph |
|---|---|---|
| CPU | 127.6 ms p50 | **106.0 ms p50** |
| GPU (Arc 140T iGPU) | compile fail | compile fail |
| NPU (AI Boost) | compile fail | compile fail |

- CPU fp32 BEATS CPU int8 (dynamic-quantization kernel overhead > memory win
  at this size). Drop the int8 copy for CPU workers.
- Torch full-pipeline decision was 162 ms; OV graph-only is 106 ms (frontend
  overhead ~56 ms -> real optimization target later).

## Failure root causes (precise)

1. GPU: `GatherND` has NO kernel in the Intel GPU plugin ("No layout format
   available for gathernd"). Worse: the plugin's op-support QUERY falsely
   reports support, so HETERO:GPU,CPU assigns it to GPU and dies at build.
   Explicit rt_info affinity pinning to CPU does NOT save it - boundary
   reorders still reference the layout-less node. (OpenVINO bug territory.)
2. NPU: two stacked blockers - (a) exported graph has unbounded dynamic dims
   (fixable via model.reshape to captured shapes), (b) after reshaping, the
   vpux compiler still rejects the graph ("Node 0 doesn't respect Custom
   Operator format") - ORT dynamic-int8 ops AND fp32-graph ops both rejected;
   GatherND likely among them.
3. ONNX Runtime DirectML EP (iGPU alternative): session creates and DML
   activates, but run() fails with an unreadable (GBK-mangled) error.

## Consequences for PandoSI

- Phase-1 EU reality on Intel: **CPU is the only EU that compiles Laya today**.
  106 ms/decision on a laptop CPU is perfectly usable for decision swarms
  (Anthropic's own edge analysis used orders of magnitude slower devices).
- Multi-EU shape B on one device still works at process level (multiple CPU
  replica workers); GPU/NPU paths are future work with four options:
  a) ONNX graph surgery: rewrite GatherND -> GatherElements (GPU/NPU-friendly)
  b) upstream: OpenVINO GPU gathernd kernel (file an issue with this repro)
  c) NPU-specific: export with option_layout static + NNCF PTQ (U8) instead of
     ORT dynamic int8
  d) DirectML EP debugging (error is garbled; may be op support)
- HETERO/MULTI on this graph: MULTI:GPU,CPU compiled (3.7s) and served
  243 ms p50 - slower than pure CPU, no reason to use it today.
