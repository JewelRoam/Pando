# Research Round 92 — A non-OpenVINO ecosystem joins the same quorum

Date: 2026-10-14

## Problem

Every Intel execution unit (CPU, iGPU, NPU) runs through ONNX Runtime or
OpenVINO. The RTX 3070 stem added in round 65 used ONNX Runtime **CUDA** —
a different device, but still the same inference ecosystem and the same
`laya` agent wrapper. So the swarm had only ever been shown to bind one
ecosystem across many devices. The open question: does the HTTP contract
actually decouple membership from the runtime, or was ecosystem sameness
quietly baked into the protocol?

## Change

Added a native **PyTorch** Laya backend, `TorchLayaBackend` in
`pandosi/backend.py`, and wired it to the stem as `--backend laya`:

```bash
.venv-cuda/Scripts/python -m pandosi.stemd \
  --node-id nvidia-3070-torch --backend laya --device CUDA \
  --root http://127.0.0.1:PORT --pairing-token-file TOKEN
```

It loads the same checkpoint with `laya.load(model, device=...)`, which is
the transformers/torch path rather than `ONNXAgent`, and answers the same
typed question. Properties kept from the ONNX backend:

- **fail closed**: CUDA is refused if `torch.cuda.is_available()` is false,
  and again if Laya resolves to a non-CUDA device, so a host cannot answer
  under a `torch-cuda` label without a real CUDA path;
- **serialized inference**: one lock around `predict`, because a single
  torch model is not safe for concurrent forwards from the threaded server;
- **stable checkpoint identity**: `torch-cuda` / `torch-cpu`, distinct from
  `onnx`, `onnx-cuda`, `onnx-gpu`, `onnx-npu`, so the root's diversity-aware
  quorum picker treats it as its own lineage group.

`tools/hetero_http_check.py --torch-stem` adds this worker to the live
swarm. `tools/torch_laya_bench.py` exercises the backend directly and
skips cleanly where torch is absent.

## Verification

Direct backend bench on the RTX 3070:

```text
loaded torch-cuda in 9.5s device=CUDA
choice=retry p=0.6498 p50=25.1ms min=23.2ms over 7 runs
```

Live four-worker quorum, `python tools/hetero_http_check.py --yes
--torch-stem --skip-npu`:

```text
registered : intel-cpu-ort, intel-igpu-openvino,
             nvidia-3070-cuda, nvidia-3070-torch
checkpoints: onnx, onnx-gpu, onnx-cuda, torch-cuda
tier       : auto   responded: 4/4
wire p50   : 181.2 ms   fanout p50: 177.9 ms
```

Two ecosystems — OpenVINO/ONNX Runtime on the Intel side and native
PyTorch on the NVIDIA side — voted in one consensus quorum with no
protocol change. The root did not know or care which runtime produced a
vote; only `checkpoint` identity and EWMA latency differentiated the
workers. Report: `metrics/hetero-checks/hetero-*.json`.

The wire contract these four workers satisfy is now written down in
`docs/STEM-PROTOCOL.md`, with no framework named anywhere in it.

## What this establishes

Heterogeneous membership in PandoSI is a property of the protocol, not of
the software stack. A device contributes a `/decide` endpoint and a
checkpoint name; the root aggregates. That is the precondition for the
elastic/unlimited-reproduction direction: a new device never needs a port
of our code, only a conformance to three endpoints.

## Remaining limitations

- one host, one GPU: the CUDA worker is a separate process and environment
  but not yet a separate machine, so this shows ecosystem independence, not
  network-distance independence;
- the Intel iGPU and the NVIDIA CUDA workers share one physical GPU-parity
  memory budget on this laptop, so contention is real but unmeasured;
- the PyTorch path is heavier to start (9.5 s, ~2 GB) than the ONNX path;
  the round does not yet compare per-decision cost across all four;
- concurrent `/decide` on the torch stem is serialized, so its throughput
  under a large quorum is unmeasured.
