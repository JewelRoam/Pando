# RTX 3070 (CUDA) worker

PandoSI can add an NVIDIA GPU as another HTTP stem without changing the
root protocol. The worker uses `onnxruntime-gpu`; the existing Intel CPU,
iGPU, and NPU workers remain on their original runtimes.

## Environment

Use a separate environment because `onnxruntime` and `onnxruntime-gpu`
provide the same import name:

```bash
python -m venv --system-site-packages .venv-cuda
.venv-cuda/Scripts/pip install onnxruntime-gpu==1.31.0
nvidia-smi
```

Verify the provider before starting a worker:

```bash
.venv-cuda/Scripts/python -c \
  "import onnxruntime as ort; print(ort.get_available_providers())"
```

Expected:

```text
['TensorrtExecutionProvider', 'CUDAExecutionProvider',
 'CPUExecutionProvider']
```

## Run a CUDA stem

```bash
.venv-cuda/Scripts/python -m pandosi.stemd \
  --node-id nvidia-3070-cuda \
  --root http://ROOT_IP:8080 \
  --pairing-token-file ~/.pandosi/stem-pairing.token \
  --backend onnx \
  --onnx-path artifacts/laya-en-fixed.onnx \
  --device CUDA
```

The backend refuses to start if the first provider is not
`CUDAExecutionProvider`, so a misconfigured machine cannot silently
run a CPU worker under a CUDA label.

The graph is still Laya; the difference is the execution backend and
the protocol-level checkpoint identity (`onnx-cuda`).

## Verify live hot-plug

```bash
python tools/hetero_http_check.py --yes --hotplug-cuda
```

This starts the Intel workers first, then joins the CUDA stem into the same
running root quorum.
