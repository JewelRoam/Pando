01 / CORRECTION 
Laya、JEV 没拼错：它们改变了“拼智能”的基本单位 
上一版把二者误判为语音转写错误，这是错误的。Laya 是可本地部署的开源 System One 决策模型；JEV 是 TypeSafe AI 的闭源 API。它们都不是逐 token 生成文本，而是针对给定 state，一次前向输出类型化决策与置信度。 
上一版错误前提 
把“小设备拼智能”等同于“把一个 LLM 切到很多设备”，因此只比较了 pipeline、tensor parallel 与多 Agent。 
更新后的问题 
把智能拆成 
state 表征 → typed decision → planning → tool use → expression 。其中高频判断可交给 421M 级决策模型并行处理；LLM 只承担开放式推理与表达。 
证据边界： Laya 官方仓库为本轮直接读取；JEV、Ollama/llama.cpp 生态及大部分 2026 项目数据来自搜索索引抓取。页面将这两类证据分开，不把 index 结果写成实测。 
02 / SYSTEM ONE 
决策模型不是“小一点的聊天模型” 
它不生成一段推理文本，而是对 Choice / Score / Noul 等 typed question 给出答案与经过标定的概率。对多设备系统而言，这意味着最合理的扩展方式是 复制、分工、集成 ，而不是切分 843MB 权重。

03 / ENGINES 
引擎横向比较：弹性发生在哪一层 
“支持分布式”并不等于“节点可随时加入退出”。下表把异构设备、发现、热扩缩、重分片与故障恢复拆开看；没有一个现成引擎同时覆盖所有能力。

Petals 
研究型、公共 swarm 已死 
Python / PyTorch 节点；按 Transformer blocks 做 pipeline。 
DHT 寻址、广播 block 区间、client reroute；设计上支持 join / leave 与定期 rebalance。

Exo 
实验性、Apple 中心 
Mac / Apple 设备为主，支持 pipeline / tensor；报告未找到 Android 或 Raspberry Pi 支持。 
LAN P2P 自动发现；可按拓扑与内存重新分区，但不是推理中的无缝热加入。 
项目仍活跃（约 47k stars），但评测仍称 experimental；不能据此承诺机顶盒可用。

SGLang 
服务副本弹性 
GPU 服务器栈；TP / EP / DP / CP / PP 与 prefill-decode 分离。 
同一模型分片内部不支持运行时增减设备；依赖外部 load balancer 扩缩副本。 
适合数据中心服务，不支持手机与 CPU 机顶盒混搭；弹性发生在 replica 层。 
引擎层结论： Petals 的机制最接近“任意节点动态加入”，但公共 swarm 已不可依赖；Exo 最接近异构局域网体验，却不是机顶盒栈；llama.cpp RPC 最容易自己动手，但发现、安全和恢复都要外补；vLLM / SGLang 的弹性属于数据中心。

E / EXPERT PARALLEL 
MoE 专家并行 
跨弱设备无路径

#2 · BACKGROUND 
B：pipeline / TP 大模型 
只服务于必须保留“一个大模型”且允许低速的后台任务。复刻 Anthropic 15 盒 pipeline，或以 distributed-llama 的 Pi 5 tensor parallel 为性能参照。 
先固定同构硬件与模型分片，不从任意异构设备热加入开始。 
用外部 coordinator 做发现、健康检查、整链重启；不要把 llama.cpp RPC 当安全生产服务。 
Petals 可研究其 DHT 思路，但不依赖公共 swarm。 
最先验证： 掉线恢复时间、KV 重建成本、持续吞吐与功耗。
