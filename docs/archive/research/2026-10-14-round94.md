# Research Round 94 — Pipeline staging measured: the link is free, the device is the wall

Date: 2026-10-14

## Question

Round 93 proposed a rule — stage a model across devices only while the
inter-stage link cost `L` is below per-stage compute `T` — but never ran it.
This round cuts the real Laya graph, chains the halves over real HTTP, and
measures.

## What was built

- `tools/stage_split.py` — splits one ONNX graph at a node boundary into
  stage A (`nodes[:cut]`) and stage B (`nodes[cut:]`). The interface is the
  set of tensors produced by A and consumed by B. Initializers stay external
  and are shared, so splitting does not duplicate the 1.7 GB weight blob.
- `tools/stage_pipeline_check.py` — captures a real tokenized decision feed
  from the Laya ONNX agent, runs stage B as an HTTP server, and measures
  latency and throughput of the chain against the single-device forward.

## Correctness first

Chained stages must reproduce the single-device outputs exactly, or the
measurement is meaningless. The check asserts `allclose(atol=1e-4,
rtol=1e-4)` on both graph outputs (`logits`, `act_logits`) for every cut
tested; it passes. Splitting the graph changes the transport, not the math.

Note that stage B also needs the small original inputs its nodes still read
(`marker_pos`, `marker_mask`, `qtype`); they travel with the activations.

All times in milliseconds. `balance` is `min(T_a,T_b)/max(T_a,T_b)`: 1.0 is
an even cut, 0.0 means one stage is the whole model.

## Findings

**1. The interface is tiny and the link is essentially free.** Across cuts
the activation payload is 0.15-1.22 MB in 2-16 tensors, and the loopback
round trip is 1-2 ms against 19-63 ms of per-stage compute. `L < T` holds by
more than an order of magnitude everywhere on one host.

**2. Same-host staging buys no throughput.** Measured at equal concurrency
(1/2/4 requests in flight, baseline measured the same way), the throughput
gain is 0.95x-1.13x — noise around parity. This is the central result:
**`L < T` is necessary but not sufficient.** Pipelining moves work between
stages; it does not create compute capacity. When both stages share one CPU,
the CPU is the bottleneck in either arrangement, and the extra HTTP hop can
only add overhead.

**3. Staging always costs single-request latency.** Sequential two-stage
latency was +1.4 ms to +24.6 ms over the single-device forward. A pipeline
only pays at two or more requests in flight, and only when it adds capacity.

**4. The refined rule.**

```text
stage  iff  L < per_stage_compute            (link is cheap, round 93)
       and  the stages occupy disjoint compute resources   (round 94)
else   replicate
```

The second clause is the operative one. It is also exactly the
heterogeneous-fusion case this project exists to test: stage A on the RTX
3070 and stage B on the Intel iGPU are disjoint, whereas two processes on
one CPU are not.

## Cross-device: the only configuration the rule permits

Same cut (900), stage A on the RTX 3070 (`CUDAExecutionProvider`), stage B on
the Intel CPU, baseline = the whole model on the RTX 3070:

| measurement | value |
|---|---:|
| T_full (whole model, CUDA) | 13.70 ms |
| T_a (half, CUDA) | 6.71 ms |
| T_b (half, CPU) | 41.70 ms |
| L (loopback round trip) | 1.17 ms (min) |
| single-device throughput | 76.1 req/s |
| two-stage throughput @4 in flight | 35.4 req/s |
| throughput gain | **0.47x** |
| added latency | +50.4 ms |
| verdict | **replicate** |

Devices are disjoint here, the link is nearly free, and staging still loses
badly — because the split gives the slow device half the work. The 3070
finishes the whole model in 13.7 ms while the CPU needs 41.7 ms for its
half, so the critical path is 41.7 ms instead of 13.7 ms. Offloading to a
slower device is not free parallelism; it is a downgrade of the bottleneck.

Balancing the split to the device speeds (give the 3070 ~86% of the nodes)
would put the critical path near 11.8 ms, a ~1.1x throughput gain, at the
price of roughly doubling per-request latency. That is the whole upside of
pipeline parallelism with one fast and one slow device, and it requires the
cut to land at a node whose cost ratio matches the device speed ratio.

**Implementation consequence for PandoSI.** For a heterogeneous swarm the
default must stay replicate-and-vote (data/agent parallel): every device
runs the whole model, the votes are aggregated, and no device is ever the
bottleneck for another. Staging is worth building only for the cases the
rule cannot otherwise cover — the model does not fit on one device, or the
devices are throughput-comparable so the split is nearly even.

### A numerical side effect worth recording

Chaining across providers is not bit-identical: stage A on CUDA vs the same
graph on CPU differed by up to 5.3e-4 in `logits`, consistent with NVIDIA
TF32 being on by default. A pipeline split across providers therefore
produces slightly different numbers than a single-device run, which matters
for a system that compares votes across nodes. The same-provider chain
(CPU->CPU) reproduces the single-device output within 1e-4.

## Two methodology traps found (and fixed) in this round

- **Unequal concurrency.** Comparing a staged path with 4 requests in
  flight against a single-device baseline run one at a time produced a fake
  **1.93x** gain. Measured at equal concurrency the gain disappears. The
  tool now measures the baseline at the same concurrency.
- **ORT thread oversubscription.** With the default `intra_op_num_threads`
  (one per core) and three sessions in one process, `T_full` was 445-535 ms;
  pinned to 4 threads it is 80-91 ms. The multi-session oversubscription was
  also inflating the measured link cost to ~130 ms. Both are recorded so
  later rounds do not re-measure the noise.

## Next experiment

The cross-device measurement above closed the pipeline question for the
current hardware: one 3070 dominates this CPU, so no split of the whole
model can beat it. The open case is the one the rule still allows —
**throughput-comparable devices**: two GPUs of the same class, or an iGPU
taking a proportional share. Measure the cut that matches the device speed
ratio (not the 50/50 cut) and check whether the theoretical ~1.1x bound is
reachable in practice. On this host that needs the second GPU the round-92
note asked about.
