# Research Round 68 — LAN-interface HTTP path

Date: 2026-10-14

## Question

Can the tokenized root/stem protocol operate through the host's real LAN
interface, rather than only through loopback, without changing the quorum
contract?

## Change

`stemd` now separates:

- `--host`: interface to bind (`0.0.0.0` for LAN reachability);
- `--advertise-host`: address reported to root (defaults to `--host`).

The distinction is required because binding to `0.0.0.0` and advertising
`0.0.0.0` are not equivalent. Root must receive a dialable address.

## Experiment

`tools/lan_http_check.py`:

1. creates a 15-minute temporary `lan_listen` grant;
2. starts root with `--lan` on a free high port;
3. starts one loopback-advertising stem;
4. starts one LAN-advertising stem bound to `0.0.0.0`;
5. verifies both register with the same root and token;
6. sends eight decisions through one quorum containing both workers.

## Result

Host LAN address: `192.168.31.100`.

| stem | observed EWMA |
|---|---:|
| loopback-advertised | 6.81 ms |
| LAN-IP-advertised | 5.48 ms |

Wire p50 for the two-worker decision stream: **17.40 ms**.

The LAN/loopback EWMA ratio was 0.80. That does **not** mean LAN is faster:
both endpoints are on the same physical host, so this only proves the
protocol works through the LAN interface and that the observed values are
within scheduler noise. It is not a remote-network measurement.

## What is proven

- root LAN binding is gated by the expiring `lan_listen` grant;
- a stem can bind a LAN interface while advertising a dialable address;
- root reaches the LAN-advertised stem through the real interface;
- both workers remain in one checkpoint-diverse quorum;
- token protection and node statistics continue to work.

## What is still unproven

Real multi-host latency, packet loss, firewall traversal, and WAN
partition behavior require a second physical device. Those numbers must
not be inferred from this same-host experiment.
