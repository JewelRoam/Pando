# Research Round 125 — What a device can and cannot do with the model it has

Date: 2026-10-15

## The question the elastic premise turns on

Round 123 priced independence: a member whose errors do not travel with the
others is worth several points to the ensemble even when it is 19 points
*less* accurate than the rival for its seat. Every member this project has
produced sits in one family, so the load-bearing question is whether a single
device holding a single graph can contribute a second opinion.

`tools/same_family_voter_check.py` scores three candidates in one harness:
the same graph with the ballot reversed, the quantised sibling the project
would actually ship to an NPU or a set-top box, and (by default) any graph
named on the command line. Each re-runs one lineage over the recorded dev
split and asks how far it moves the base's vote and whether the ensemble
improves when it joins.

## Two answers, both clean

**The ballot is not an input.** `typed-decisions` with its eight candidates
presented in the opposite order flipped **0 of 240** answers - phi +1.000
with its own original vote, ensemble unchanged. Whatever the model is using,
it is not the position of the options. (Round 120's narrower ballot *did*
move answers, but that removes options rather than reordering them; a device
cannot mint a second opinion by shuffling.)

**Quantisation moves decisions but not information.** `laya-en.int8.onnx`
against the fp32 `english` base it was quantised from:

| | value |
|---|---:|
| flips vs `english` | **48/240 (20.0%)** |
| accuracy | 80.00% (against `english`'s 85.42%) |
| phi vs `english` | **+0.413** |
| phi vs `multilingual` / `typed-decisions` | +0.229 / +0.319 |
| ensemble at the gate's coverage | 95.92% -> 95.92% |
| ensemble at full coverage | 89.17% -> 87.08% |

Twenty per cent of answers change, so the quantised graph is genuinely a
different function - unlike the fine-tuned descendant, which agreed on every
task. But its errors still arrive with the family's: phi +0.41 is inside the
neural trio's own range (+0.23 to +0.53), and it buys the ensemble nothing at
matched coverage while costing 2.1 points at full coverage. The noise
quantisation adds is shared with the base it came from.

Caveat, and a real deployment one: the int8 graph was scored with the fp32
calibration table, because the project has no calibration for the quantised
checkpoint. A sibling that will run on a different accelerator needs its own
temperature before its confidence can be trusted in a weighted vote.

## The diversity spectrum, now measured end to end

| variation | split | answers differently | phi | ensemble effect |
|---|---|---:|---:|---|
| fine-tuned descendant (`rlcd-v7` vs `english`, round 119) | dev | 0/240 (0%) | +1.000 | -5.0 points |
| reversed ballot (same graph, this round) | dev | 0/240 (0%) | +1.000 | none |
| quantised sibling (int8 vs `english`, this round) | dev | 48/240 (20.0%) | +0.413 | none at matched, -2.1 full |
| prompt re-rendering (`english` vs `typed-decisions`) | dev | 34/240 (14.2%) | +0.453 | the trio's own baseline |
| outside the family (`bayes` vs the trio, round 123) | held-out | **51-55%** | **+0.07** | **+4.1 matched, +3.8 full** |

The ordering is monotone in phi and *anti*-monotone in everything a device
would naturally optimise: accuracy (the outsider was the least accurate
member tested), novelty of the file (the descendant was a different file with
different weights), and effort (the descendant was the expensive one).

(The first four rows are the dev split and the last is the wording-held-out
split, because that is where each was measured. Rather than assume the two
splits are alike, the trio's own phi was recomputed on each: **+0.21 to +0.53
on dev against +0.36 to +0.82 on the wording-held-out split** - the lineages
are *more* correlated on wording none of them has seen, because unfamiliar
phrasing is exactly where they make the same mistake. Difficulty moves the
whole family together, which is the strongest form of the argument below.)

What separates the last row from the rest is not that it was built
differently - it is that its mistakes come from a different mechanism.
Re-rendering, retraining a descendant, and quantising all perturb a function
while preserving its error structure; only a different mechanism of deciding
produces errors that do not co-occur.

## What this closes

The elastic premise cannot be satisfied inside the family, and the project
should stop looking for diversity there. Growth by replication buys
throughput; growth by re-rendering buys nothing; a fleet that is
heterogeneous only in *bit-width and prompt* is homogeneous where it counts.
A heterogeneous fleet is worth building only if the devices differ in what
they are, and the next member should be chosen by its measured divergence
(round 123's table, now this tool's output) rather than by its accuracy or
its novelty.
