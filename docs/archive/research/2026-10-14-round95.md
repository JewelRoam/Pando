# Research Round 95 — Two ecosystems, one mind: the runtime does not change the decision

Date: 2026-10-14

## Question

Round 92 proved a native PyTorch stem can join the same quorum as the
OpenVINO/ONNX Runtime stems. That is a protocol result. The question that
actually matters for "拼凑起一个智能" is behavioural: when two devices run
**the same model through different ecosystems**, do they vote the same way?

If they do not, a heterogeneous quorum is a mix of different minds and every
consensus number is suspect. If they do, the runtime is a transport detail
and vote diversity must come from the model, not the stack.

## Experiment

`tools/cross_ecosystem_check.py` loads the Laya English checkpoint twice on
one host — `OnnxLayaBackend` (ONNX Runtime, CPU) and `TorchLayaBackend`
(native PyTorch, CUDA) — and answers the same graft suite with both. The
script runs in the CUDA environment, which carries both runtimes.

Suite: 27 choice tasks (`assets/graft_suite.jsonl` also holds 13 `noul`
tasks, which the two-voter comparison does not cover).

## Result

```text
chkpoints     : onnx (ONNX Runtime CPU) vs torch-cuda (native PyTorch)
agreement     : 27/27 (100.0%)
accuracy      : onnx 55.6% | torch 55.6%
split         : both correct 15 | both wrong 12 | only-onnx 0 | only-torch 0
confidence gap: mean 0.0028, max 0.0134
latency p50   : onnx 14.8 ms | torch 24.9 ms
2-voter quorum: auto 14 | verify 13
```

**The ecosystem does not change the decision.** Every one of the 27 tasks
got the same choice from both runtimes, the per-task confidences differ by
0.3% on average, and the two runtimes are equally right and equally wrong —
there is not a single task where one runtime was correct and the other was
not. The runtimes are not merely compatible; they are behaviourally
identical on this suite.

## Why this matters

1. **Heterogeneous replicas are interchangeable.** A device can join the
   swarm with whatever runtime it has and its vote carries the same weight
   as any other. Nothing in the consensus needs to know which stack produced
   a vote, which is the precondition for the elastic-membership direction.
2. **Vote diversity must come from the model, not the runtime.** Round 57
   measured 32.5% cross-lineage divergence and round 74 showed distinct
   checkpoints splitting 11/12 tasks over HTTP. That is where disagreement
   comes from — different model versions, not a different inference engine.
   A heterogeneous swarm is therefore a legitimate ensemble: adding a device
   adds a replica of the same mind unless it also brings a different
   checkpoint.
3. **The 14/13 auto/verify split is a confidence artifact, not a
   disagreement.** With two voters, `aggregate()` returns `auto` when the
   mean calibrated probability clears the gate and `verify` otherwise; the
   two voters never actually disagreed. A two-voter quorum is too easy to
   agree, which is also why the project's default `min_quorum` is 3.

## Caveats

- one checkpoint (English) and one suite (27 choice tasks); the
  multilingual and typed-decision checkpoints are not covered here;
- "behaviourally identical" is measured on this suite, not proven in
  general — a task near a decision boundary could still flip between a
  roughly-equal and a marginally-different numeric path;
- the cross-provider numerics from round 94 still apply: chaining *within*
  a decision across providers moves `logits` by ~5e-4, so a pipeline split
  across providers can in principle flip a near-tie even though the two
  runtimes as whole-model voters do not.

## Next step

Repeat the comparison for the multilingual and typed-decision checkpoints,
and add a near-boundary task set (cases where the top-two option
probabilities are within a few percent) to test whether runtime-level
numerical differences ever flip a vote. That is the failure mode this round
cannot rule out.
