# Research Round 116 — Judging a bet properly, and remembering a loss

Date: 2026-10-14

## Two weaknesses in the rollback from round 115

Round 115 made the supervisor treat a growth as a bet and undo it if it lost.
The bet was judged from a *single* latency sample taken one cooldown after the
change, and the loss was not remembered - so the loop could propose exactly
the same change again.

## A median, not a sample

The bet now collects `rollback_samples` (3) decision-latency readings, or
waits until `rollback_window_s` elapses, and compares the median against the
latency measured before the growth.

```text
round 3: hold: evaluating growth reproduced-1: sample 1/3
round 4: hold: evaluating growth reproduced-1: sample 2/3
round 5: hold: growth reproduced-1 paid off: median 95 ms vs 371 ms before it
```

Both verdicts have now been observed on the same mechanism: growth #1 paid
off (median 95 ms against 371 ms), growth #2 did not (median 420 ms against
106 ms).

## Capacity accounting

A rollback must not remove a member the swarm has come to depend on, so
`rollback_allowed` refuses when removing the node would leave fewer than
`keep` members, or when the node is the only member that has answered
anything. Note what it deliberately does *not* ask: whether the node is
fast. A harmful growth can add a fast member that makes everyone else slower -
that is exactly round 114's result - so "is this node good" is the wrong
question; "can the swarm serve without it" is the right one.

## The oscillation, found by running it long enough

With the single-sample bet fixed but no memory, the loop did this:

```text
round 10: retire: rollback (median 420 vs 106 ms)
round 12: cooling down
round 14: grow -> reproduced-3        <- the same change, re-proposed
round 15: p50= 848.7 ms members=4
```

Rolling back was not enough. As soon as the trigger fired again the
supervisor proposed the identical change, and the swarm paid for it a second
time. The run ended at 848.7 ms, worse than if it had never rolled back.

**A rollback is evidence, and it was being thrown away.** The supervisor now
remembers `(host, checkpoint) -> the measurement that rejected it`, with a
TTL (`bad_candidate_ttl_s`, default 30 minutes), and refuses that candidate
while the memory holds:

```text
round 13: hold: 112 ms is slow, but growing onto 127.0.0.1/english was
          rolled back earlier (median 420 ms against 106 ms): the same change
          was measured and rejected
```

Same run, now stable to the end:

| | reproductions | final p50 |
|---|---:|---:|
| no memory | 3 | 848.7 ms |
| with memory | 2 | **144.1 ms** |

The swarm grew, judged both bets correctly, undid the one that lost, and then
stopped asking for a change it had already measured and rejected - while
still reporting that it is over target.

## What this says about self-tuning systems here

Three distinct failures appeared in three consecutive rounds, each only
visible after the previous one was fixed:

```text
round 114: growth can hurt          (measured, not assumed)
round 115: a hurt change must be undoable
round 116: an undone change must be remembered, or it repeats
```

Each was found by running the loop for longer, not by reading it. A
self-tuning loop needs three things that are easy to add one at a time and
worthless alone: a judgement, a reversal, and a memory.

## Verification

19 smoke tests, extended with: `rollback_allowed` refusing when the target is
the only member that has served anything and when `keep` would be breached,
the negative memory blocking a repeat, a different host not being tarred with
the same brush, and the memory expiring with its TTL. `retirement_check`,
`elastic_loop_check`, `swarm_check` and `autonomy_check` pass.

## Open

- the memory is keyed by `(host, checkpoint)` and never re-tested while it
  holds. A host that gains capacity - a GPU freed, other work stopped - will
  never be reconsidered inside the TTL, and an operator has no way to clear
  one entry except by restarting the supervisor.
- the TTL is one number for every kind of failure: a transient warm-up cost
  and a structural "this host cannot take another worker" expire together.
- the supervisor still has no notion of *cost*: a member that is slow but
  cheap is treated exactly like one that is slow and expensive, which is the
  question an operator would actually be answering.
