# Research Round 112 — Category by declaration, not by keyword

Date: 2026-10-14

## The defect round 111 named

Round 111 gave the adaptive quorum a per-category floor, and then pointed at
its own weakest link: the category was decided by scanning the question text
for `security`, `suspicious`, `phishing` or `threat`. A playbook question
called `risk_check`, whose instructions read "Rate whether this account
should be frozen", matches nothing - so the one question in the playbook that
most needed four voters would silently have been given two.

The failure mode is the one this project keeps re-meeting: a value used as
though it carried a guarantee it does not. A string match is not a
classification.

## Declared categories

A playbook question may now declare its category:

```toml
[[questions]]
id = "risk_check"
type = "choice"
category = "security"
criteria = ["freeze", "allow"]
```

`Playbook.question_categories` maps ids to categories, and
`Coordinator._category_floor` resolves in this order:

1. **declared category** - the id the client sends must be a playbook id when
   a playbook is loaded, so this is an exact lookup, not an inference;
2. **fail conservative** - a question that a *categorised* playbook does not
   classify gets the most demanding declared floor, not the default one;
3. **keywords remain, but only upward** - a question whose text matches a
   security word still gets the security floor even if the playbook called it
   ordinary, so the old behaviour can never be less safe than before;
4. no playbook, no categories: the CLI floor, unchanged.

## Measurement

Six serialized replicas, adaptive quorum, target 120 ms, playbook floor 2 for
ordinary questions and 4 for security ones:

| question (declared) | concurrency | throughput | p50 | quorum settled |
|---|---:|---:|---:|---:|
| `risk_check` (**security**) | 1 | 11.9 req/s | 81.8 ms | 5 |
| `risk_check` | 8 | 26.0 req/s | 259.1 ms | **4** |
| `intent` (ordinary) | 1 | 12.4 req/s | 79.7 ms | 5 |
| `intent` | 8 | 36.0 req/s | 177.3 ms | **2** |

`risk_check` contains no security keyword in its id *or* its instructions, so
under round 111's rule it would have run at k=2. It now holds k=4, and the
price is explicit: **28% less throughput under load** (26.0 vs 36.0 req/s)
and a slower tail, for twice the independent voters on the question where a
miss is worst. Both questions keep the full quorum of 5 while idle, because
the floor only binds when the latency target pushes.

## What this changes

The per-category scheme is now *policy*, not pattern matching: the operator
writes down which questions deserve protection, the floor follows the
declaration, and the only remaining inference path can raise the floor and
never lower it. The safety property of round 111 ("a security decision never
falls to the serving floor") no longer depends on how carefully someone named
a question.

## Verification

The smoke test for this grew rather than multiplied: it now also asserts that
a declared `security` category gets the security floor, a declared `ordinary`
one gets the ordinary floor, an unclassified question in a categorised
playbook fails conservative, and a keyword match still raises the floor.
`swarm_check`, `slow_stem_check`, `autonomy_check` and the rest are
unaffected - without a playbook the floor logic is unchanged.

## Open

- the category vocabulary is free-form. Nothing checks that a declared
  category has a matching `[gating.<category>]` table, so a typo
  (`categoy`) yields a category that never contributes a floor of its own
  and silently falls back to the ordinary one; validation would be a small,
  useful addition.
- categories are per question id, not per question *type* or per action, so a
  playbook that wants "anything that can trigger an action is protected" has
  to remember to say so on each question.
- the elasticity loop is still open at the top: the swarm can now tune its
  quorum, retire a device and reproduce onto one, but nothing decides when to
  grow. A supervisor that watches latency at the floors and calls
  reproduction (or retirement) on its own is the next step.
