# Research Round 134 — The CPU is the wrong silicon to vote with

Date: 2026-10-15

## The question that started this

Rounds 132-133 concluded that the host CPU is the ceiling and that adding
compute units buys nothing. Both were measured on an *idle* machine. A
personal computer is not idle: the CPU is the part that is always busy - the
browser, the editor, this agent - while the GPU and the NPU sit unused. The
question worth asking is therefore not "which unit is fastest on an empty
machine" but **"what does each unit cost the host, and what survives when the
host is loaded"**.

Measuring that turned up two defects in the harness itself, both of which
had to be fixed before any number could be trusted.

## Two harness defects

**`blocked` does not isolate a unit.** `Coordinator.blocked` is retirement
bookkeeping; `pick_quorum` never consults it, and only `retire()` removes a
node from the registry. Every "one unit alone" cell in rounds 132-133 set
`blocked` and was in fact served by a *rotating mix* of all registered
stems. The per-unit attributions in those rounds are withdrawn; their
structural findings (k divides throughput; extra units add nothing to a
host-bound fleet) were measured on the fleet as a whole and stand.

**The loader repeated one task.** A hundred identical requests measure the
per-request overhead and any caching, not the model. The driver now cycles
distinct states.

With isolation by construction (only the unit under test is started), distinct
tasks, per-response accounting (`tier`, `quorum_size`, `responded`), host
CPU-seconds read from the OS for the stem process, and a host load of eight
background processes for the "busy" phase:

| unit | host idle | host loaded | host CPU per decision |
|---|---:|---:|---:|
| CPU (ONNX Runtime) | 16.8 /s | **6.0 /s** | 791 ms -> **1647 ms** |
| Intel iGPU (OpenVINO) | 171 /s | 341 /s | 6.6 ms -> 5.1 ms |
| Intel NPU (OpenVINO) | 268 /s | 296 /s | **1.4 ms -> 1.8 ms** |

(four concurrent clients, 120 decisions per cell; the loaded column has eight
of the machine's logical cores burned by unrelated busy processes)

## What the corrected numbers say

**The CPU is the wrong silicon to vote with.** It is an order of magnitude
slower at serving decisions, it loses **64% of its throughput** when the host
is loaded, and it costs the machine **791-1647 ms of host CPU per decision**
against the NPU's 1.4-1.8 ms - roughly a factor of 500-1000. The CPU stem is
not a voter that happens to be slow; it is the only member whose work
competes with the user's own.

**The accelerators are not merely idle capacity; they are load-invariant.**
The iGPU and NPU barely move when eight cores are taken away (171 -> 341,
268 -> 296 decisions per second; the iGPU's *rise* is client-side scheduling
under load, not a faster device). Their host-side cost per decision is
single-digit milliseconds, so a fleet built on them keeps serving while the
machine is busy and gives the CPU back to whatever the user is doing.

**This is the answer to the objective's "one device, several compute units".**
The value of the iGPU and NPU on a personal computer is not peak throughput on
an empty machine - rounds 132-133 correctly found little of that - it is that
they are the only units that are *available* when the machine is in its normal
state.

## What this changes in the code's priorities

`pick_quorum` orders candidates by in-flight calls and a coarse latency band.
With units this unequal, the quantity that ordering should optimise is the
one this round measures - **host CPU per decision** - and the stem already
reports the statistics it would need. A device that cannot afford to be busy
should not be chosen while a cheaper one is idle, however fast its own
clock is.
