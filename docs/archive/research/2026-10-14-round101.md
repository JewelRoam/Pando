# Research Round 101 — Where the calibration rule belongs

Date: 2026-10-14

## The defect being fixed

Round 100 found that temperature is selected by the checkpoint string a stem
reports. A device that registers as `en` instead of `english` runs an
identity temperature instead of the fitted 3.2, so it silently votes with an
uncalibrated confidence in a gate whose thresholds assume calibration. No
error, no warning, different behaviour.

## First attempt, and what it broke

The obvious fix is to fail closed in the coordinator: if any vote lacks a
calibration table, withhold the `auto` tier. That was implemented and it
worked — and it broke every synthetic harness in the repository.

`tools/swarm_check.py`, `tools/slow_stem_check.py`, `tools/autonomy_check.py`
and the LAN/remote/latency harnesses all run the deterministic
`MockBackend`, whose checkpoints are named `mock-0`, `loopback`, `lan`,
`group-b`, `rlcd-v7` and so on. None of those have calibration tables, so
every one of them would have lost the `auto` tier and failed its
assertions - including two checks that run in CI.

That is the finding worth recording: **the coordinator is shared by
production and by every test rig, so a hard safety rule placed there
couples the safety property to test fixtures.** Either the rule gets
weakened to accommodate the rigs, or every rig has to fabricate calibration
data. Both are worse than putting the rule where the risk actually is.

## What was actually changed

**The coordinator reports; the actor enforces.**

`rootd`:

- warns once, at registration, that a checkpoint has no temperature table
  (`[calibration] checkpoint 'x' has no temperature table; its votes cannot
  justify an autonomous action`);
- includes `uncalibrated_checkpoints` in the decision result.

It does not change the tier, so no existing harness or deployment shifts
behaviour.

`pandosi/autonomy.py`:

- `AutonomyLoop(require_calibration=True)`, on by default. A decision whose
  result lists uncalibrated checkpoints is **held**, with the reason naming
  them. Acting is the thing that can hurt, so the strictness lives in the
  component that acts.

`assets/calibration/mock.json`:

- the synthetic voter declares its own identity calibration, explicitly and
  in one place, instead of the policy being relaxed for it. The file records
  why: MockBackend's probabilities are already on a usable scale, so a
  declared identity is honest, while a real device reporting an undeclared
  identity is still treated as uncalibrated.

## Verification

```text
python -m unittest discover -s tests      -> 11 tests OK
python tools/autonomy_check.py --yes      -> acts with the declared calibration
python tools/swarm_check.py --yes         -> status OK
python tools/slow_stem_check.py --yes     -> status OK
```

The new smoke test drives a real root with three real HTTP stems whose
checkpoint has no table, and asserts the consensus is genuinely strong
(`tier != escalate`, unanimous) while the loop still refuses to act and
names the uncalibrated checkpoint. The two CI harnesses were re-run
specifically as a blast-radius check, because that is what the first
attempt broke.

## Still open

The coordinator cannot distinguish "this device is intentionally named
`mock`" from "this device is misnamed". The durable fix is for identity to
be *declared and verified* rather than inferred from a free-form string:
carry the lineage id in the playbook or in the spore manifest that
authorises the node, and refuse a stem whose declared identity has no
calibration entry. That also closes the older observation from round 91
that all manifests are signed by one key - identity, authorisation and
calibration should come from the same declaration.
