# Research Round 91 — Peer fetch of missing parent manifests

Date: 2026-10-14

## Problem

Round 90 gave every node a manifest cache, so a joiner could tell three
states apart: `valid`, `parent-missing`, `invalid`. But a node that
received only a *descendant* (the common case: a grandchild spore arrives
from a peer that already advanced past the parent) could never move out of
`parent-missing`. It recorded provenance it could not check.

For a system whose whole claim is "reproduction is auditable", a joiner
must be able to *obtain* the missing link and verify it, not just report
that it is absent.

## Change

Manifests are now addressable by content hash, and a joiner fetches the
missing parent from the same peer it pulls payloads from.

Serving side:

```text
GET /spore/manifests/<manifest_hash>   -> signed manifest JSON, or 404
```

`SporeServer` and `rootd` both serve a manifest history keyed by
`manifest_hash()` (the SHA-256 of the signed manifest excluding the
Ed25519 signature). `rootd` seeds its history with its own root manifest;
`SporeServer` accepts a `history={hash: manifest}` argument so a seed that
already advanced can hand out its ancestors.

Joining side:

```text
ensure_parent_lineage(base_url, child, cache_dir, verify_key, auth_token)
  -> (status, detail)
```

It first runs the Round 90 cache check. Only if the status is
`parent-missing` does it:

1. fetch the parent manifest from the peer by hash;
2. require `manifest_hash(fetched) == requested hash`;
3. require a valid Ed25519 signature under the pinned root key;
4. store it and re-run the cache check.

Status semantics after the round:

```text
valid           lineage present and verified (possibly after a fetch)
parent-missing  peer could not serve it, or the fetch failed
invalid         local history is present and contradictory
untrusted       peer returned a wrong-hash or bad-signature manifest
```

`join --spore` refuses on `invalid` and `untrusted`; it prints
`parent-missing` as a warning and continues, because not having enough
history to check is not the same as having contradicting history.

## Verification

`tools/spore_dag_check.py` now drives a live server:

```text
missing parent fetched from peer and verified
peer without the parent leaves lineage unverified
peer returning a different manifest rejected
peer returning a bad signature rejected
```

The last case exploits the fact that `manifest_hash` excludes the
signature: a manifest with a zeroed signature still hashes to the requested
digest, so only `verify_manifest` catches it. This is exactly why the fetch
path checks the signature and not just the hash.

`tools/spore_chain.py` shows the realistic flow at hop 3: node D holds only
the hop-3 manifest and bootstraps the missing hop-2 parent over HTTP from
the serving peer (`generation 2 links to <hash>`).

`tools/spore_root_check.py` (new) starts a real `pandosi.rootd` subprocess
and checks the whole serving surface:

```text
root pubkey served
root manifest verified (generation 0)
manifest served by content hash
unknown manifest hash -> 404
wrong pairing token -> 403
```

Unit smoke suite: `python -m unittest discover -s tests` -> 10 tests OK.
The new tool is wired into `.github/workflows/swarm.yml`.

## Remaining limitations

- the fetch is one level deep; a long lineage still needs repeated calls
  (or a batched "give me the chain" endpoint) to reach the root;
- all manifests are signed by one key, so a fetch proves integrity, not
  which node produced the manifest;
- merge semantics for multi-parent nodes are still undefined;
- a malicious peer can still withhold a manifest (denial of provenance),
  but cannot forge one.
