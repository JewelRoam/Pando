# Research Round 100 — The gate verified end to end, and the defaults survive tuning

Date: 2026-10-14

## Question

Round 99 measured the gate offline (92.9% at 51.8% coverage). Two things were
still open: does that number survive the real wire path, and what thresholds
should the playbook actually ship?

## Finding 1: calibration is selected by the checkpoint *name*

Re-checking round 99 turned up a coupling worth recording. `Calibrator`
caches per checkpoint string and looks up `assets/calibration/<name>.json`.
Round 99 named the lineages `en` / `ml` / `td`, which match no file, so the
temperature was identity and the curve described **raw** confidences. The
production names carry fitted temperatures:

```text
english.json           temperature 3.2   raw_ece 0.391 -> calibrated 0.2456
multilingual.json      temperature 3.8   raw_ece 0.427 -> calibrated 0.2645
typed-decisions.json   temperature 5.0   raw_ece 0.169 -> calibrated 0.0881
```

With those applied, the production-faithful curve is:

| configuration | auto coverage | accuracy on acted | confidence (correct vs wrong) |
|---|---:|---:|---|
| raw confidences (round 99) | 51.8% | 92.9% | 0.825 / 0.427 |
| production calibration | **48.1%** | **92.3%** | 0.661 / 0.482 |

Calibration compresses confidence (as designed) and costs 3.7 points of
coverage for 0.6 points of accuracy. The conclusion from round 99 holds, but
the numbers move.

**The robustness lesson:** a stem's *name* silently selects which
temperature is applied. A device that registers as `en` instead of `english`
runs a different gate with no error and no warning. Checkpoint identity is
being used as a capability key, and those are not the same thing. This is a
real defect for a system meant to accept arbitrary devices.

## Finding 2: the threshold sweep was wrong the first time

`tools/gate_tune.py` sweeps `auto_min_agreement` and `auto_min_probability`
over the recorded decisions. Its first run recommended `agreement >= 0.33`,
which would have shipped a gate that acts on a **1-2 minority vote**.

The bug: a three-way split produces `agreement = 1/3`, but `aggregate()`
returns `choice = None` for it (a tie is not a majority). Those 4 of 27
decisions can never be acted on whatever the threshold is, so they must be
excluded from the candidate set instead of counted as coverage. With ties
excluded the sweep sees only majority agreements (0.667 and 1.0).

This is the same failure shape as rounds 94 and 97: a plausible metric
computed on the wrong set. It also means the *lower* bound of the agreement
threshold is structural - with a 3-voter quorum there is nothing between
0.667 and 1.0.

## Finding 3: the shipped defaults are already at the operating point

```text
27 decisions (4 three-way ties carry no choice)
baseline accuracy        51.8%
current defaults 0.60/0.60 -> coverage 48.1% at 92.3%
best pair (target 90%)    0.6667/0.55 -> coverage 48.1% at 92.3%
```

No threshold pair beats the current `0.6 / 0.6` on this suite for a 90%
target. The playbook default is therefore kept, now with evidence rather
than as a guess.

## Finding 4: live equals offline, exactly

`tools/gate_e2e_check.py` starts a real `rootd` and three real ONNX lineage
stems over HTTP, drives the round-98 autonomy loop over the labeled suite,
and compares what the loop achieved against the local prediction:

```text
tasks                27
acted / held         13 / 14        (tiers: auto 13, verify 14)
live coverage        0.4815
live accuracy        0.9231   (12 of 13)
held accuracy        0.1429   ( 2 of 14)
offline coverage     0.4815
offline accuracy     0.9231
coverage delta       0.0000
accuracy delta       0.0000
```

**Identical to four decimal places.** The whole chain is faithful: stem
produces a vote, the root stamps the checkpoint it learned at registration,
looks up that checkpoint's temperature, calibrates, aggregates, gates, and
the loop decides. Nothing in the wire path drifts from the local model of it.

The `held` number is the one that matters operationally: the 14 decisions
the loop refused to act on were right 14.3% of the time (2/14). The gate is
not holding a random half of the work; it is holding almost exactly the
decisions that were wrong.

## What this establishes

The gate is now a *verified* component with a measured operating point:

```text
unattended coverage : ~48% of decisions
accuracy on that    : ~92%
error rate avoided  : the held set is 14% accurate, 2/14
cost                : one aggregation over votes already collected
```

That is the concrete answer to "can it act on its own?" - yes, on half the
workload, at roughly 92%, with the rest recorded for review. It is the
strongest end-to-end result the project has, and it was obtained without a
larger model anywhere in the loop.

## Caveats

- 13 acted decisions is a small sample; 12/13 has a wide interval, and the
  exact 92% should not be treated as a stable constant;
- the thresholds were tuned and evaluated on the same 27 tasks. The shipped
  default was not changed, so nothing was fitted-in-place, but any *new*
  threshold must be chosen on a split and confirmed on the other half;
- one question type (choice) and one language;
- the checkpoint-name/calibration coupling from Finding 1 is still in the
  code; a stem misnamed by a single character changes the gate silently.

## Next step

Two candidates, in order of leverage:

1. **Fix the calibration coupling** (Finding 1): key calibration by a
   declared lineage id carried in the playbook or the spore manifest rather
   than by the ad-hoc checkpoint string a stem reports, and fail loudly when
   a stem's identity has no calibration entry.
2. **Out-of-sample threshold selection**: split the suite, tune on one half,
   confirm on the other, and only then consider changing a shipped default.
