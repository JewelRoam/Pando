# Research Round 66 — Parallel quorum fan-out

Date: 2026-10-14

## Change

`Coordinator.decide()` now sends the decision payload to all selected stems
concurrently through a bounded `ThreadPoolExecutor`, preserving the original
quorum order when collecting votes. Node failures still shrink the quorum
instead of blocking the decision.

The root response now includes `fanout_ms`, separating coordinator dispatch
latency from HTTP and serialization overhead.

## Four-runtime HTTP result

The same live swarm as round 65 was used:

| worker | runtime | checkpoint |
|---|---|---|
| Intel CPU | ONNX Runtime CPU | `onnx` |
| RTX 3070 | ONNX Runtime CUDA | `onnx-cuda` |
| Intel iGPU | OpenVINO GPU | `onnx-gpu` |
| Intel NPU | OpenVINO NPU | `onnx-npu` |

All decisions returned four votes from four distinct checkpoints.

| measurement | sequential round 65 | parallel round 66 |
|---|---:|---:|
| wire p50 | 430.5 ms | **237.8 ms** |
| root fan-out p50 | (not exposed) | **226.3 ms** |
| first decision | 952.3 ms | 541.2 ms |

The steady-state decisions in the parallel run were 170.3–311.4 ms. The
improvement is about **1.81x at p50** without changing the model, graph,
workers, or quorum semantics.

The remaining fan-out latency is now approximately the slowest worker
(NPU class), plus HTTP overhead, rather than the sum of all workers.

## Correctness evidence

- four workers registered;
- four checkpoint identities appeared in every vote matrix;
- every decision returned `responded=4`;
- existing dead-node and token-gating smoke tests still pass;
- a new unit test installs a 250 ms artificial transport delay and proves
  three quorum calls overlap (`peak=3`, elapsed < 500 ms).
