# Research Round 65 — RTX 3070 via ONNX Runtime CUDA + HTTP consensus

Date: 2026-10-14

## Hardware and software

- GPU: NVIDIA GeForce RTX 3070, 8 GB, compute capability 8.6
- Driver: 616.56, CUDA UMD 13.4
- Runtime: `onnxruntime-gpu==1.31.0` in an isolated project venv
- Providers: `TensorrtExecutionProvider`, `CUDAExecutionProvider`,
  `CPUExecutionProvider`
- Graph: the same dynamic `artifacts/laya-en-fixed.onnx` used by the CPU
  ONNX stem

The host's original PyTorch is CPU-only (`2.14.1+cpu`) and the global
ONNX Runtime exposes only DML/CPU. CUDA integration therefore does not
replace the Intel/OpenVINO path; it is an additional worker runtime.

## Benchmark: same graph, same real inputs

`tools/cuda_bench.py` captured real ONNXAgent tensors and ran the identical
graph with CUDA and CPU providers:

| provider | p50 | p95 |
|---|---:|---:|
| RTX 3070 CUDA | **15.0 ms** | **16.7 ms** |
| Intel CPU ORT | 125.6 ms | 137.1 ms |

Result: **8.36x lower p50 latency on CUDA**.

The raw logits are not bit-identical: maximum absolute difference was
0.4600. This is small relative to the decision margins in the tested
suite, but it is not zero and must not be described as identical numerics.

## Decision parity

The full 14-task English graft suite was run through both providers using
the same tokenizer and graph:

- answer agreement: **14/14 (100%)**
- GPU accuracy: 78.57%
- CPU accuracy: 78.57%
- maximum calibrated confidence delta: **0.0009**

This supports using CUDA as another quorum member, while retaining the
existing rule that confidence and disagreement must be calibrated and
verified rather than assumed.

## Heterogeneous HTTP swarm

`tools/hetero_http_check.py` launched four independent OS processes:

| worker | runtime | checkpoint |
|---|---|---|
| Intel CPU | ONNX Runtime CPU | `onnx` |
| RTX 3070 | ONNX Runtime CUDA | `onnx-cuda` |
| Intel iGPU | OpenVINO GPU | `onnx-gpu` |
| Intel NPU | OpenVINO NPU | `onnx-npu` |

All four registered through the same tokenized HTTP root protocol. The
root selected a four-checkpoint quorum and returned four votes for every
decision.

Steady-state wire latency:

- p50: **430.5 ms**
- first decision: 952.3 ms (warm-up)
- four subsequent decisions: 389.8–455.5 ms

This demonstrates the intended architecture: the coordinator does not
need a shared runtime or a shared accelerator API. OpenVINO and CUDA
workers cooperate at the protocol layer.

## Negative result found during the run

The first four-way attempt configured the iGPU with a 128-token bucket
against a 256-token static graph. OpenVINO correctly failed with:

```text
The input tensor size is not equal to the model input type:
got [1,128] expecting [1,256]
```

The CPU, CUDA, and NPU workers registered and voted, but the run was
rejected as incomplete. Re-running with the graph-matching 256 bucket
produced the full four-worker result above.

## Reproduction

```bash
python -m venv --system-site-packages .venv-cuda
.venv-cuda/Scripts/pip install onnxruntime-gpu==1.31.0
HF_HOME=D:/PandoSI/.hf-cache .venv-cuda/Scripts/python tools/cuda_bench.py --runs 15 --json
python tools/hetero_http_check.py --yes
```

The CUDA environment is intentionally isolated: installing
`onnxruntime-gpu` beside the global CPU/DML package can shadow the CPU
runtime used by the existing stems.
