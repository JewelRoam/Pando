# Research Round 130 — One device, several compute units, one opinion

Date: 2026-10-15

## The objective's first clause, re-measured under the new rules

Rounds 54-56 verified a triple-execution-unit consensus on this machine, long
before the project learned that a second device running the same lineage is
not a second opinion (rounds 119, 121) and that neither is a correlated
family (rounds 128, 129). Two stems running one lineage on two compute units
is the textbook case of the first rule, so it is worth knowing that the
hardware claim still holds *and* that the aggregation now treats it
correctly.

`tools/multi_eu_swarm_check.py` starts real stems over loopback and asks the
240 wording-held-out questions twice: once of each compute unit directly
(fidelity and speed), and once of the fleet through the quorum.

## The two compute units are the same voter, 1.6x apart in speed

| | CPU (ONNX Runtime) | Intel iGPU (OpenVINO) |
|---|---:|---:|
| accuracy, 240 held-out tasks | 75.42% | **75.42%** |
| identical choices | \multicolumn{2}{c}{**240 / 240**} |
| median confidence gap | \multicolumn{2}{c}{0.0002} |
| median latency | 79 ms | **53 ms** |
| decisions per second | 12.3 | **18.0** |

The iGPU is 1.5x the throughput of the CPU on the same weights and gives the
same answer on every task, to within a 0.0002 confidence difference. That is
the strongest form of the round-95 result (cross-ecosystem votes agree), now
measured across *hardware* rather than across runtimes on one device.

It also means the second unit cannot change a decision - not as a
probabilistic statement, but by construction: two voters that answer
identically on every row are one voter with two addresses. What the second
unit buys is 18.0 - 12.3 = **5.7 decisions per second**.

## What the quorum does with two devices and one lineage

The fleet registered four stems - `english` twice (once per unit),
`typed-decisions` once, and the cheap text member - with lineage counting on.
Every decision reported **3 opinions for 4 stems**: the two `english` stems
collapsed into one voice, which is exactly the round-121 rule doing its job
on hardware rather than on a replay.

The fleet's majority accuracy over the 240 held-out tasks is 77.9%, and the
saved report carries the invariant explicitly: because the units voted
identically on every compared row, removing one cannot change any decision.

## What is not in the fleet, and why

The NPU is not a member. The current OpenVINO (2026.4.1) vpux compiler rejects
the graph:

```
vpux-compiler: Got non broadcastable dimensions pair : '-1' and -9223372036854775808'
  loc(fused<{name = "node_MatMul_215", type = "MatMul"}>)
```

preceded by the front end failing to infer upper bounds for
`gnr1_gather_el` (GatherElements) and `node_bitwise_and_1` (LogicalAnd). The
GPU had its own op-level blocker of the same family - `No layout format
available for gathernd:node_GatherND_29`, the GatherND issue
`tools/fix_gathernd.py` was written for - and the rewritten graphs
(`artifacts/laya-en-static-fixed.onnx`, `laya-en-fixed.onnx`) compile on the
iGPU in 12-15 seconds.

So the state of the silicon on this machine is:

| unit | runtime | state |
|---|---|---|
| CPU | ONNX Runtime | works, 13.0 decisions/s |
| Intel iGPU | OpenVINO | works with the fixed graph, 20.8 decisions/s |
| Intel NPU | OpenVINO | **blocked**: unbounded shapes reach the vpux compiler |

The NPU blocker is op-level and specific - a MatMul whose dimensions reach
the compiler as `-1` and `INT64_MIN`, i.e. dynamic where it must be static.
That is the same class of problem rounds 52-54 solved twice, and it is now
the project's most concrete piece of unfinished hardware work.
