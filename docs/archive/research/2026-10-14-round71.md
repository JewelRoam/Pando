# Research Round 71 — Live CUDA hot-plug into a running swarm

Date: 2026-10-14

## Question

Can the RTX 3070 be added to a running PandoSI root after Intel CPU, iGPU,
and NPU workers are already serving decisions, without restarting root or
changing its quorum configuration?

## Experiment

`tools/hetero_http_check.py --hotplug-cuda`:

1. starts root and the Intel CPU, iGPU, and NPU stems;
2. makes two decisions using the three-checkpoint baseline;
3. launches the CUDA stem under the same token and root;
4. waits for registration;
5. makes five decisions using all four checkpoints.

No root restart or reconfiguration occurs.

## Baseline

| measurement | value |
|---|---:|
| workers | 3 |
| checkpoints | `onnx`, `onnx-gpu`, `onnx-npu` |
| responded | 3/3 |
| baseline fan-out | 150-240 ms |

## Hot-plug

The CUDA stem took **11.81 seconds** from process launch to registration.
That time is dominated by loading the 1.7 GB Laya graph and initializing the
CUDA session, not by the registration protocol.

After registration, every decision returned all four checkpoints:

```text
onnx, onnx-cuda, onnx-gpu, onnx-npu
```

| worker | EWMA at end |
|---|---:|
| RTX 3070 CUDA | 81.2 ms |
| Intel iGPU | 83.4 ms |
| Intel CPU | 90.2 ms |
| Intel NPU | 158.2 ms |

Post-hot-plug wire p50 was 203.2 ms and root fan-out p50 was 180.6 ms.
The slowest worker class, the NPU, remains the dominant fan-out floor.

## Interpretation

This combines the two previous properties:

- elastic membership: a worker can join a live coordinator;
- heterogeneous execution: the new worker uses a different runtime and
  accelerator API from the existing workers.

The unified HTTP contract does not require all workers to share OpenVINO,
CUDA, model files, or runtime libraries. The cost visible to the user is
mostly the new worker's model-load time.

## Limitation

All processes remain on one host. A real multi-host test still needs to
measure network setup, firewall behavior, and remote failure recovery.
