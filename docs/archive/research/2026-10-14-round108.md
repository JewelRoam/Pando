# Research Round 108 — Delta replication, end to end

Date: 2026-10-14

## Two things round 107 left undone

Round 107 built content-defined chunking and a content-addressed store, and
measured a 15.3x reduction in bytes on the wire. It also left two gaps: the
delta was slower in *wall time* than a full transfer (thousands of small
files read back), and the live replication path did not use it at all -
`rootd --serve-spore` still served v1 fixed-size manifests and `join` still
pulled them.

## Packed chunk store

Chunks now live in one append-only `chunks.bin` with a text index, plus a
bounded in-memory cache for chunks written during a pull (a pull reads back
what it just wrote). On the same pair as round 107, verified byte-identical:

| leg | bytes | transfer | assemble | total |
|---|---:|---:|---:|---:|
| cold, batched | 1610.5 MB | 5.04 s | 5.30 s | 10.49 s |
| warm, delta | **105.0 MB** | **0.345 s** | 5.46 s | **5.84 s** |

The wall-clock regression is gone: assembly fell from 45.76 s to 5.46 s, and
the delta is now **faster overall than a full transfer (5.84 s vs 10.49 s)
while moving 15.3x less data**. Before this change the delta looked like a
loss on loopback; that was the store's layout, not the idea.

## Wired into replication

```text
rootd --serve-spore <payload> --chunking cdc     # manifest v2 + POST /spore/blobs
join  --spore --chunk-store <dir>                # reuse what is already held
```

`join` also writes `spore-cache/<node>/pull-stats.json`, so a supervisor can
read what a replica actually received instead of trusting a log line.

## End-to-end result

`tools/delta_replication_check.py` — two real roots, two real joiners, real
HTTP, two real 1.7 GB model loads, both replicas registering as workers:

```text
parent  lineage=english   registered=True  wire=1610.5 MB  pulled=5222  reused=0
child   lineage=rlcd-v7   registered=True  wire= 105.0 MB  pulled= 338  reused=4870
reduction 15.3x, child_chunks_reused 4870
```

The second device - sharing the parent's chunk store - received **105 MB
instead of 1.6 GB** to replicate a different lineage, and the number comes
from the receiving side, not from the library's own estimate.

## The admission rule bit, correctly

The first run of the check failed with:

```text
playbook declares no usable lineage: ['rlcd-v7'] have no calibration table,
so no stem could register
```

Round 102's rule, working exactly as designed: a declared lineage must also
ship a calibration table. The fiction here was mine - I invented a lineage id
for the delta demo without giving it a temperature.

The fix turned out to be data the project already had: round 81 fitted
temperature 2.6704 for this exact candidate. `assets/calibration/rlcd-v7.json`
now carries it with its provenance (`n_tasks`, ECE, and the note that the
holdout slice showed no calibration improvement). This is a small example of
the security work paying for itself: it forced a declaration that existed as
knowledge in a research note but had never been made machine-checkable.

## A bug I made and caught

Adding the `/spore/blobs` route to `rootd`'s `do_POST` chain merged the
`/decide` branch into `/register` - every registration would have sent two
responses. Restored and re-verified. Worth recording how it was caught:
**not by a test**. The regression suite passed both before and after, because
every client opens a fresh connection per request, so a second response on
the same socket goes unnoticed by the tools. It was caught by re-reading the
region after editing it.

`do_POST` is a long `if/elif` chain over paths, which is exactly the shape
where this happens. A route table, or a test that asserts each route writes
exactly one response, would make it structurally harder.

## Verification

17 smoke tests; `reproduce_check` (v1 path), `autonomy_check`, `swarm_check`,
`spore_root_check`, `spore_chain`, `spore_dag_check` all green. The v1
manifest, its chunk endpoints and its behaviour are untouched, so nothing
that already worked changed path.

## Open

- **garbage collection**: chunks are never removed, so a replica's store
  grows with every lineage it has seen.
- **granularity is untuned**: 256 KiB chunks suit weight blobs; a mixed
  workload may want a different average, and the insertion-alignment
  limitation from round 107 still stands.
- **no compression**, and no resume for an interrupted pull.
- the store is still per-process-local state on disk; two replicas on one
  host share it by pointing at the same directory, which is a check-scale
  convenience rather than a design.
