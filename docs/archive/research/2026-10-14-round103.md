# Research Round 103 — Attestation: turning a declaration into a check

Date: 2026-10-14

## The gap round 102 left

Round 102 made identity declared, and admission control stops a *misnamed*
device. It does not stop an *impersonating* one: a stem can register as
`english` while executing something else, and its votes will be admitted and
calibrated as English. A declaration is a claim.

## What was built

The stem now reports the artifact it actually loaded, and a playbook can
require it to match.

```toml
[lineages]
admit = ["english", "multilingual", "typed-decisions"]

[lineages.artifacts]
english = "df95fcfb...aa483"
```

- `pandosi.spore.artifact_digest()` streams a SHA-256 over the artifact
  **and its external-data siblings**, mixing file names in.
- `stemd` computes it for the ONNX path at startup, prints it, and sends
  `artifact_sha256` with every registration.
- `rootd` refuses (`403`, with `expected_sha256` and the reported value) any
  stem whose reported digest does not match the declared one, and announces
  at startup which lineages require attestation.
- `playbook` validates the block: ids must be declared, digests must be
  lowercase 64-character hex.
- `tools/attest_graphs.py` generates the block for the local graphs; the
  artifacts are gitignored, so the digests are host-specific by design and
  the example playbook ships the block commented out.

## A flaw in the first version

The first implementation digested the graph file. For `laya-en.onnx` that
file is **3 MB**, while the weights are a separate 1.68 GB
`laya-en.onnx.data` blob. The digest would have attested a protobuf and said
nothing about the model - and a stem could have paired the attested graph
with different weights and passed.

Found by printing the file sizes rather than the hash. `artifact_digest()`
now digests every file the artifact needs (graph plus `.data` siblings),
1.1 s for the 1.7 GB set on this host, which is acceptable at worker start
and negligible next to loading the graph.

## Verification

`tools/attestation_check.py` starts a real `rootd` from a generated playbook
plus one real ONNX lineage stem, twice:

```text
laya-en.onnx digest df95fcfba58dc5f1...4aa483
declared correct digest -> registered: True
declared wrong digest   -> registered: False
ATTESTATION CHECK OK
```

The second case is the point: the *same honest stem* is refused when the
playbook declares a different artifact, because it cannot attest something
it is not running. Denied by the root's own check, not by the stem's
cooperation.

Smoke coverage (`test_declared_lineages_gate_registration`):

```text
declared lineage, no digest        -> 403 (attestation required)
declared lineage, wrong digest     -> 403
declared lineage, matching digest  -> 200
```

12 smoke tests pass; the attestation check is host-only (it needs the graph
files) and so is not in CI, while the admission logic it exercises is.

## What this closes

For a swarm that declares its lineages and their artifacts, registration now
requires three things that all come from the same declaration: a declared
identity, a calibration table for it, and a matching artifact digest. A
device cannot join by claiming; it has to be running the artifact the
operator declared.

## What it still does not close

- **the playbook is unsigned at the point of use.** Its hash travels in the
  Spore manifest, but `rootd --playbook` reads a local file and trusts it;
  whoever can write that file chooses the admitted set and the digests. The
  signing machinery exists (rounds 82-91) and is not wired here.
- **one signing key for every manifest** (round 91). Per-lineage keys would
  make the digest declaration attributable to a lineage owner rather than to
  whoever published the playbook.
- **attestation is self-reported at registration**, then trusted for the
  lifetime of the process. A stem that swaps its weights after registering
  is not detected; re-attestation on a schedule, or per-decision proofs,
  would be needed for that.

All three are the same theme as rounds 100-102: a value carrying a guarantee
it has not yet earned. The next step with the most leverage is signing the
playbook at load time and requiring the signature to come from a key that
the operator pinned, which turns the whole declaration chain into something
a third party can verify.
