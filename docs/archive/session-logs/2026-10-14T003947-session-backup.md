## 二、多设备怎么"拼成一个智能"——三种架构路线

### 路线 A：单模型分片（一台大模型摊到多台机器）

| 并行方式 | 原理 | 对弱设备的友好度 | 弹性 |
|---|---|---|---|
| **流水线并行 PP** | 每台机器存几层，串行传递激活值 | ★★★★★ 只需低带宽，Anthropic 用的就是它 | 中等：加机器=加深流水线，但延迟也线性增加 |
| **张量并行 TP** | 把单个矩阵乘法切开，每步都要全互联通信 | ★ 需要高带宽低延迟（NVLink/IB 级别），WiFi/普通以太网上基本不可行 | 差：world_size 固定，很难动态加减节点 |
| **专家并行 EP** | MoE 的不同专家放在不同机器上 | ★★★ 专家激活是稀疏的，通信量可控 | **最好**：见下面的 vLLM 弹性专家并行 |
| **数据并行 DP** | 每台机器跑一份完整模型，处理不同请求 | ★★★★★ 完全独立 | 最好：加机器=加吞吐，但单模型大小受限于单机内存 |

关于弹性扩缩容，目前最接近"运行中动态加减节点"的工程实现是 **vLLM 的 Elastic Expert Parallelism**（2026-05 发布，[官方博客](https://vllm.ai/blog/2026-05-14-elastic-expert-parallelism)）：它可以在**不重启服务**的情况下增减数据并行 worker、重新分配专家、变更拓扑——但这是 MoE 专属能力，且当前实现面向 GPU 数据中心（Ray 编排），不是 CPU 盒子集群。Ray Serve LLM 也支持跨节点 TP/PP，但定位同样是 GPU 机群（[官方文档](https://docs.ray.io/en/latest/serve/llm/user-guides/cross-node-parallelism.html)）。

**Petals** 是唯一为"互联网级志愿者节点自由加入退出"设计的引擎（[arXiv 论文](https://arxiv.org/abs/2209.01188)），它把模型切成层块分发到 swarm 中的节点，节点掉线后流量自动绕行。它最接近你说的"无限繁殖、弹性加入"的愿景，但同样受限于通信带宽，实际吞吐也不高。

### 路线 B：多代理组合（每台设备跑自己的小模型，群体协作）

这不是把一个大模型切开，而是把 N 个独立的小模型当作 N 个"小脑"，通过路由器/编排器组合成系统智能（ensemble、Mixture-of-Agents、分层 agent 编排）。**这个路线的吞吐量随设备数线性扩展**，因为请求之间互不通信，是唯一能在普通网络条件下真正"弹性扩容"的方式。Anthropic 帖子里也暗示了这种形态：大模型做战略协调，派出小模型当子代理。

### 路线 C：混合分层

一个稍强的"指挥官"模型（比如一台 mini-PC 上的 8B）+ 一群设备端 1B 以下的小模型做执行。这是当前学术界（edge AI 领域的 co-inference 研究）和工业界（Apple/Google 端云协同）都在收敛的方向。

**小结**：如果你要"一台逻辑上的大模型"，目前没有完美引擎——Petals 最接近去中心化愿景但吞吐差，vLLM 弹性 EP 最工程化但绑定 GPU/Ray。如果你要"一群小智能拼出系统智能"，数据并行多代理是现成且唯一真正可弹性的方案。

## 三、小模型能不能塞进一个 CPU？

### 密集小模型（dense）

| 模型 | 参数量 | 量化后大小 | CPU 实测表现 |
|---|---|---|---|
| **Gemma 3 270M** | 270M | ~278MB（int4） | 在树莓派 5 的 CPU 上用 LiteRT-LM 达到 **~22.6 tok/s 解码**，峰值内存 680MB（[树莓派官方博客](https://www.raspberrypi.com/news/mastering-edge-ai-on-raspberry-pi-with-litert-and-gemma/)） |
| Qwen3-0.6B / 1.7B | 0.6B / 1.7B | ~400MB / ~1GB | llama.cpp 在现代 x86 CPU 上约 5–20 tok/s，勉强可用 |
| SmolLM2-360M / Phi-3-mini | 360M / 3.8B | ~250MB / ~2.3GB | 同上量级 |

Gemma 3 270M 在纯 CPU 上确实可以流畅运行，但 270M 的能力上限非常有限，基本只能做分类、摘要、简单指令跟随，**做不了 agent**（Anthropic 的实验也证实了这一点：他们的评估发现模型在上下文短于 32K 时能力大幅下降，而 270M 级别的模型根本撑不起这种 agent 工作负载）。

### MoE 小激活模型（这可能是关键方向）

| 模型 | 总参数 | 每token激活 | 意义 |
|---|---|---|---|
| **Gemma4-26B-A4B** | 26B | ~4B | Anthropic 在 TV box 集群上跑的就是它；单机 16GB 显卡也能跑 |
| Qwen3-30B-A3B | 30B | ~3B | Jetson AGX Orin 64GB 上达 76.7 tok/s（[Anthropic 引用 NVIDIA 数据](https://developer.nvidia.com/)） |
| Gemma 3n E2B / E4B | 5B / 8B | 有效内存 ~2B / ~4B | 通过 **PLE（Per-Layer Embeddings）** 把嵌入层卸载到 CPU，让实际加速器占用等效于 2B/4B 模型（[HF 博客](https://github.com/huggingface/blog/blob/main/gemma3n.md)） |

MoE 的意义在于：**总参数大（能力接近大模型），但每步计算量小（延迟接近小模型）**。这恰好同时解决了"智能够不够"和"设备装不装得下"两个矛盾。代价是全部权重仍需驻留内存/存储——4-bit 量化后，26B 总参数约需 13–15GB 内存，所以 Anthropic 需要 15 台 4GB 盒子来分摊存储，而不是因为算力不够。

### 结论性的判断

- **一个普通 x86 CPU（8GB RAM 以上）**：能流畅跑 270M–1B 密集模型，勉强跑 2–4B（个位数 tok/s），MoE 小激活模型如果单机内存够也可以试。
- **一组 4GB 低端盒子**：单机只能跑 <1B 密集模型；要跑有意义的 agent 级模型（≥9B），必须靠流水线分片，代价就是 0.4 tok/s 这种不可用的吞吐。
- **短期内"无限繁殖成超级智能"的瓶颈不在引擎而在两处**：① 弱设备的通信带宽使任何细粒度并行（TP）都不可能；② 小模型的能力天花板——Anthropic 自己的实验里，只有 GLM-5.2（不是小模型）能完成端到端复制，Qwen3.5-9B 在 9/9 类硬件上能搭起推理，但**推理服务搭起来之后能不能"干活"是另一个量级的问题**。

## 一、Laya 和 Jev 到底是什么

两者都是 **"System 1"决策模型**——不做自由文本生成，只输出结构化的决策：选择、评分、是/否判断，带校准概率。

**Laya**（Convai Innovations，2026-09-18 发布，Apache-2.0 开源）：

- **仅 421M 参数**，基于 ModernBERT 编码器，**非自回归**——state + typed questions 进去，**一次 forward pass** 直接出 choice/score/yes-no，延迟约 **33ms**（[模型介绍](https://robot.agientry.com/en/articles/laya-open-system-one-decision-model)、[官网](https://laya.convaiinnovations.com/?curius=1940)、[GitHub](https://github.com/LeonaDavinci/laya-system-one)）。
- 训练用 RLCD（强化学习 + 严格正常则评分规则），概率是真正校准过的，不是随便的 softmax 排名。
- **CPU 部署已验证**：官方指南支持纯 CPU 本地运行（英文 checkpoint 约 808MB，[安装指南](https://laya-ai.com/guides/install-laya)）；社区已有 **OpenVINO int8 版**（[HF 仓库](https://huggingface.co/rupeshs/laya-ov-int8)，有人在 CPU 上拿它玩 Flappy Bird）、**LiteRT 版**可跑在安卓手机上（[HF 仓库](https://huggingface.co/litert-community/laya-LiteRT)）、iOS Core ML 版。**一台 4GB 内存的电视盒就能单机跑一份完整 Laya，不需要分片。**

**Jev**（TypeSafe AI，2026-09-15 发布，闭源 API，创始人 Diogo Almeida 是 ChatGPT 共同发明人之一）：

- 定位类似，但走 API 路线，被媒体称为"用决策模型替代 LLM 的更便宜方案"（[FT](https://www.ft.com/content/456884ea-2558-4648-8036-a77b73733430)、[Indian Express](https://indianexpress.com/article/technology/artificial-intelligence/meet-jev-new-ai-model-from-chatgpt-inventor-10887591)、[WSJ](https://www.wsj.com/tech/ai/startup-typesafe-ais-jev-model-sparks-copycats-talk-of-llm-alternatives-e39ff57d)）。
- 已有学术论文验证它在边缘编排中替代 LLM：在 6G 边缘网络场景下，Jev 的决策延迟比 DeepSeek 低 22.4%、比 Gemini 低 61.9%（[arXiv:2609.23136](https://arxiv.org/abs/2609.23136)、[arXiv:2609.22753](https://arxiv.org/abs/2609.22753)）。
- 有开发者用 Jev 打通了 Pokémon Red（[Tom's Hardware](https://www.tomshardware.com/tech-industry/artificial-intelligence/developer-says-jev-decision-model-beat-pokemon-red-in-under-a-week-non-llm-engine-succeeds-where-traditional-chatbots-stalled-for-months-but-claude-opus-5-coached-the-model-through-its-dead-ends)）——说明这类模型已经能驱动真实的序列决策任务。

**关键区别于生成式 LLM 的结构性事实**：LLM 解码是自回归的，一个 token 一次 forward pass，N 个 token 就是 N 次全流水线穿越——这正是 Anthropic 那个 0.39 tok/s 灾难性吞吐的根源。**决策模型非自回归，一次请求只穿越一次流水线。** 网络延迟的成本从"每个 token 一次 RTT"变成"每个决策一次 RTT"，而且还可以通过 batching 把多次决策塞进同一次穿越里摊薄成本。这直接改变了你命题的可行域。

## 二、你的拓扑混合命题：文献和工程证据

你提出的“近了用流水线、远了用数据并行”不是拍脑袋，它恰好和学术界/工业界最近两年的收敛方向一致：

### 2.1 流水线并行为什么天生抗高延迟

流水线并行的通信量极小且是点对点的——层与层之间只传一个固定大小的激活张量。AWS 的工程文档说得很直白：*"The only thing sent between stages is one activation tensor, which is small, point to point, and tolerant of network latency"*（[AWS Builder](https://builder.aws.com/content/3Hy5nQ60H31JUSY5YY5QQGBJ4Rg/distributed-llm-inference-on-aws-serving-a-70b-model-across-multi-gpu-and-multi-node-with-vllm-on-eks)）。相比之下张量并行需要每步全互联 all-reduce，在 WiFi/跨城网络上基本不可行。

跨数据中心（即广域网）用流水线的可行性已有系统性研究：**CrossPipe**（USENIX ATC'25）专门优化了跨地理位置的流水线调度（[论文页](https://www.usenix.org/conference/atc25/presentation/chen-tiancheng)）；另有研究专门探讨了“地理分布式服务器上的 LLM 推理 + 流水线并行”（[ScienceDirect](https://www.sciencedirect.com/science/article/pii/S0166531625000616)）。

### 2.2 公网上的流水线推理已经有人跑通了

**leyten/shard** 项目是目前最激进的公开实现：**GLM-5.2（744B 参数）跨美国 6 个州的 7 张消费级 GPU，走公网，流水线并行 + 推测解码，跑出约 30 tok/s**（[GitHub](https://github.com/leyten/shard)）。他们的实测数据给了一条清晰的技术路径：

| 阶段 | tok/s | 改动 |
|---|---|---|
| 纯流水线解码（每 token 一次全链穿越） | 1.87 | 延迟瓶颈 |
| + 推测解码（小 draft 模型提 K 个 token，一次穿越验证） | 1.99 | |
| + 环形直连返回（尾节点一跳回协调器） | 2.94 | |
| + 异步流水线（多个验证块同时在飞） | 16.6 | 广域网延迟降到整个循环的 ~5% |
| + CUDA-graph 化 draft | ~30 | |

关键洞察是他们的原话：*"over WAN the round-trip is the scarce resource, not compute — so speculative decoding, marginal in a datacenter, becomes the whole game."* 在数据中心里推测解码是锦上添花，在广域网上它是**唯一的救命稻草**。还有一个反直觉发现：把不持有模型层的轻量协调器放到离流水线节点近的地方（而不是留在大洋彼岸），环延迟从 174ms 降到 102ms，白赚 40%。

此外 **Intel AI PC Fleets 的预编译流水线分片**论文证明：几台普通 AI PC 通过普通网络用流水线并行能服务超过任何单机能力的模型，且在模拟广域延迟下吞吐差距进一步拉大（[HF Papers](https://huggingface.co/papers/2608.19147)）——这直接验证了“CPU 集群 + 流水线”的可行性。

### 2.3 边缘协同的成熟研究

- **EdgeShard**（IEEE IoT Journal, 2024）：首个在边缘设备+云服务器协同环境部署 LLM 的系统，用动态规划联合优化设备选择和模型切分，实测延迟降低 50%、吞吐提升 2 倍（[论文](https://doi.org/10.1109%2FJIOT.2024.3524255)）。
- **Galaxy**（arXiv:2405.17245）：利用“边缘环境中存在大量带空闲资源的可信设备”这一观察，做跨异构边缘设备的 Transformer 协同推理（[论文](https://arxiv.org/abs/2405.17245)）。
- **EdgeATP**：面向边缘集群的自适应张量并行框架（[ScienceDirect](https://www.sciencedirect.com/science/article/abs/pii/S1383762126001797)）。
- **推测解码 + 流水线**的边缘协同已有完整研究线：[arXiv:2510.11331](https://arxiv.org/abs/2510.11331)（异构边缘网络）、[FlowSpec](https://arxiv.org/abs/2507.02620)、[DiP-SD](https://arxiv.org/abs/2604.20919)、[PipeSD (ICML 2026)](https://proceedings.mlr.press/v306/han26k.html)——这条线的共同主题是：小模型在边缘做 draft，大模型在云端/远端做验证，流水线掩盖网络延迟。

## 三、把它组装起来：一个具体的系统架构

你的场景是“多个群组，组内近、组间远”。我把它形式化为一个**三层分层拓扑**：

```
┌─────────────────────────── 全局协调层（WAN）───────────────────────────┐
│   Group A (城市1)    Group B (城市2)    Group C (城市3)   ...        │
│   ┌──────────┐        ┌──────────┐        ┌──────────┐              │
│   │ 本地协调器│        │ 本地协调器│        │ 本地协调器│              │
│   ├──────────┤        ├──────────┤        ├──────────┤              │
│   │ 节点1 (L1)│        │ 节点1 (L1)│        │ 节点1     │              │
│   │ 节点2 (L2)│        │ 节点2 (L2)│        │ 节点2     │              │
│   │ 节点3 (L3)│        │ 节点3 (L3)│        │ ...      │              │
│   │ (流水线)  │        │ (流水线)  │        │ (可分片)  │              │
│   └──────────┘        └──────────┘        └──────────┘              │
└──────────────────────────────────────────────────────────────────────┘
   组间：数据并行（每组的模型是完整副本或独立智能体）
   组内：流水线并行（或单机独立运行小模型）
```

### 3.1 组内（LAN，低延迟高带宽）：流水线并行

- 如果跑的是 **Laya 级别（421M）** 的模型：一台 CPU 盒子就装得下，**根本不需要分片**，每台设备跑一份完整模型反而是更好的选择（下面会讲为什么）。
- 如果要跑更大的模型（比如 Jev 的未来开源复刻、或者一个 26B-A4B 级别的 MoE）：按 Anthropic 的方式做层间流水线分片，每台盒子存几层，LAN 延迟 <1ms，token 吞吐虽然低但可用。

### 3.2 组间（WAN，高延迟低带宽）：数据并行 / Agent 并行

- 每个群组是一个**独立完整的决策单元**，可以跑不同模型、不同任务。
- 全局协调器做请求路由：按地理就近、按负载均衡、或按能力（某组擅长某类决策）。
- 弹性扩缩容发生在这一层：**新群组上线 = 数据并行度 +1，不需要任何模型重分片**。这就是你要的“无限繁殖、弹性加入”——加副本是唯一真正零成本的弹性操作。

### 3.3 对决策模型的特殊加成：跨副本共识

数据并行架构在生成式 LLM 上只是简单吞吐叠加，但在**决策模型**上它解锁了一个生成模型做不到的能力：**多数投票/概率融合**。因为决策模型的输出是校准过的概率而非自由文本，你可以：

- 把同一个决策请求发给 k 个群组副本，收 k 个独立判断；
- 做**多数投票**（k≥3，容忍个别群组被干扰/出错）；
- 或做**概率平均**（利用校准概率做贝叶斯融合，提升整体可靠性）。

这在广域网上是**天然的容错机制**——任何一个群组掉线、被劫持或输出异常，只要超过半数副本达成一致，系统依然给出正确决策。这与 Docker Swarm 的 quorum 机制、Raft 共识的思想一致（[Docker 官方文档](https://docs.docker.com/engine/swarm/admin-guide/swarm-size-and-fault-tolerance/)）：奇数个副本，容忍 n/2-1 个故障。

### 3.4 分层编排：System 2 在核心，System 1 在边缘

你的架构天然对应“快思考/慢思考”的分层：

- **System 2（慢、深、贵）**：一个生成式 LLM 或大决策模型，可以放在某一个群组（甚至云端），处理需要推理、规划、综合的任务。
- **System 1（快、浅、便宜）**：每个边缘群组的 Laya 级模型，处理日常的 routing、意图分类、安全判断、工具选择、异常检测。
- 协调器用 System 1 做第一层过滤：简单决策就地解决（<50ms），复杂任务才路由给 System 2。

这正好是 [DRAGON 框架](https://huggingface.co/hayulalab/dragon-framework-paper/blob/main/paper.md)（分层多智能体编排，用 A2A 协议连接从边缘设备到服务器级硬件的异构智能体）和 [arXiv:2601.21822](https://arxiv.org/abs/2601.21822)（"分层边缘上的 LLM 智能体协同编排"）所探索的方向。

## 四、"让它先跑起来”的最小可行实现

既然你说了不管智能程度和速度，只求跑通，我给出一个具体到工程选型的方案：

### 方案一：纯 Laya 副本池（最简单，1-2 天可跑通）

```
每台设备：
  - pip install transformers
  - 下载 convaiinnovations/laya (808MB)
  - 跑一个 FastAPI 服务，暴露 POST /decide

一台协调器（任何一台设备兼任）：
  - 维护节点注册表（心跳/ gossip）
  - 收到请求 → fan-out 到 k 个节点 → 收集概率 → 多数投票或平均
  - 新节点注册进来 → 自动加入下一轮 fan-out
```

不需要任何分布式推理引擎。Laya 是一个标准 HF Transformers 模型，一台 CPU 盒子一份。数据并行 = fan-out，共识 = 投票。这就是“几十台设备拼成一个智能”的最小版本——每个决策的智能来自 k 个独立视角的融合，而不仅仅是单模型。

### 方案二：流水线分片（如果模型 >单机内存）

用 llama.cpp 的 RPC 后端或 EdgeShard 的思路手动写一个 thin pipeline runner：

- 模型按层切成 N 段，每台设备加载一段；
- 请求从协调器进入 stage 0，激活值沿 LAN 逐段传递，尾节点返回 logits；
- 对决策模型（非自回归）来说，**一个请求只穿越一次**，LAN 内总延迟 = Σ(每段计算时间 + 传递时间)，通常 <200ms，完全可用。

### 方案三：跨广域流水线（挑战性最高，但已有人跑通）

参考 leyten/shard 的路径：广域网纯流水线确实延迟受限（1.87 tok/s），但如果目标只是"跑起来"而不是“跑得快”，那就直接接受这个吞吐。对决策模型来说更不是问题——一次穿越 200ms，意味着每秒 5 个决策，对多数决策路由场景完全够用。

## 二、核心问题：纯决策模型能否自己走通“无限繁殖”？

这是你问的最关键的问题，答案分三层，我尽量诚实。

### 2.1 决策模型的本质：它是“政策”，不是“大脑”

Laya/Jev 的输入输出契约是：**给定的 state + 给定的问题集 → 类型化决策 + 校准概率**。它不会生成文本、不会自己发明要问的问题、不知道 `apt-get` 和 `adb connect` 是什么。它是一个**条件反射弧**——给定刺激（state），输出反应（decision）。它缺的东西恰好是“繁殖”这个目标最需要的：

1. **状态构建**——什么算“当前处境”？谁来把传感器/文件/网络信息变成 state 文本？
2. **问题生成**——该问自己什么？选项列表从哪来？
3. **程序性知识**——在陌生设备上该跑什么命令？（Anthropic 实测：9B 的 LLM 能在 9 类硬件中的 8 类上搭起推理，靠的是预训练里见过的海量运维知识；421M 的编码器模型根本没有这种知识容量）
4. **长时程规划与自我修正**——失败后换策略？记住教训？

### 2.2 证据：只有决策模型的系统走不远

最有说服力的实证来自 Jev 打 Pokémon Red 的案例（[Tom's Hardware](https://www.tomshardware.com/tech-industry/artificial-intelligence/developer-says-jev-decision-model-beat-pokemon-red-in-under-a-week-non-llm-engine-succeeds-where-traditional-chatbots-stalled-for-months-but-claude-opus-5-coached-the-model-through-its-dead-ends)）：Jev 一周内通关了，**但前提是 Claude Opus 5 在背后给它当教练，帮它走出死胡同**。没有教练的纯决策模型，面对开放环境会卡死在局部最优。

Anthropic 自己的结论也一致：小模型作为 agent 单打独斗能力有限且不会好好用顾问，但他们明确写道——*“协调更可能以大模型处理高层战略、派出小模型作为子代理的形式发生”*（[Anthropic 研究帖](https://www.anthropic.com/research/self-replicating-ai)）。

### 2.3 但是：有一个今天就能走通的中间形态

纯 Laya 走不通 ≠ 需要一个大模型实时在线。正确的分法是把“智能”拆成**三个时间尺度**：

| 层 | 谁来做 | 频率 | 在哪 |
|---|---|---|---|
| **战略层（playbook）** | 一个 LLM（或人类）写一次 | 写一次，偶尔更新 | 开发机上 |
| **策略层（决策）** | Laya 群 | 每秒几千次 | 每台设备 |
| **簿记层（状态、网络、复制）** | 普通代码 | 持续 | 每台设备 |

**具体到“无限繁殖”**：playbook 定义繁殖循环的骨架（扫描→访问→传权重→起服务→派生副本），每一步内的**环境适应性判断**交给 Laya——这台设备是什么架构？这个端口该不该试？这个 payload 校验通过了吗？该继续还是放弃？这些都是 bounded typed decisions，正是 Laya 的舒适区。

关键洞察：**LLM 的角色从“运行时依赖”降级为“离线顾问”**。它不需要在集群里实时响应——playbook 失效时，集群把失败日志打包发回开发机，LLM 离线分析、更新 playbook、推一个新版本。运行时每台设备只有代码 + 421M 权重，零外部依赖。这就是“能自己走通”的现实版本——不是靠决策模型凭空变聪明，而是靠**把 LLM 的智能一次性编译进 playbook，再让决策模型群在边缘高频执行**。

### 2.4 终极形态：从“繁殖”到“进化”

你那份报告里的 F2 路线（分布式 RLCD）其实是这个愿景里最深刻的一步，值得单独强调：

- **复制权重 = 繁殖**（生物学的无性分裂）
- **自训练权重 = 进化**（生物学的适应与选择）

如果集群能在本地产生决策数据、用 RLCD 自我微调（Hivemind / [INTELLECT-2](https://www.primeintellect.ai/blog/intellect-2) 已证明去中心化分布式 RL 可行），那“无限繁殖”就不只是数量增长，而是**质量随代际提升**——这才是真正对得起“无限繁殖”这个词的版本。今天这条路是研究前沿，不是工程现实，但它是你“开源出去最牛逼”的目标应该指向的方向。

## 首推：Physarum（多头绒泡菌）

如果你只看一个选项，看这个。它的概念贴合度不是“像”，是**字面上完全一致**：

**学名 *Physarum polycephalum* 的直译就是"多头的黏液"**（poly = 多，cephalum = 头，slime = 黏液）。它同时命中了你所有的设计目标：

1. **单一生物，无数细胞核，没有细胞壁**——Physarum 的营养体是一个巨大的多核单细胞，数千个细胞核共享同一份细胞质，没有隔膜把它们分开。这**字面上就是“异构硬件融合为一个统一智能”**：不同设备 = 不同细胞核，协议 = 共享细胞质，没有防火墙（细胞壁）。
2. **没有大脑，却有智能**——它没有神经系统，但通过自组织的运输管网络解决了东京地铁网络优化问题（[PMC 论文](https://pmc.ncbi.nlm.nih.gov/articles/PMC4594612/)）。这就是你项目的核心主张：每个节点很蠢，但网络整体有智能。
3. **Anthropic 自己的比喻就是"digital slime mold"**——他们的研究帖原文把 AI 蠕虫比作“缓慢、分布式的数字黏菌”（[Business Insider 引述](https://www.businessinsider.com/ai-worms-digital-slime-mold-nightmare-fuel-anthropic-2026-10)）。你拿这个名字，等于直接接住了 Anthropic 抛出的梗，任何读到 Anthropic 帖子的人都会立刻 get 到。
4. **弹性扩缩容是它的生存方式**——食物多就向前生长，食物少就收缩撤退，环境恶劣就变成干的硬壳休眠，条件好了再萌发。这就是你的“弹性扩缩容”。
5. **命名空间干净**——GitHub 上只有几个图形模拟项目（[JS/WebGL 模拟](https://github.com/nicoptere/physarum)、[Rust/WGPU 模拟](https://github.com/tom-strowger/physarum-rust)），没有任何基础设施框架用这个名字。`physarum` 这个 org/repo 名大概率抢得到。

**附带命名体系**（这是选它还有个隐藏加分项——一个项目名好不算好，全家桶名字都好才是真牛逼）：

| 组件 | 名字 | 对应含义 |
|---|---|---|
| 整体系统 | **Physarum** | 统一智能体 |
| 单个设备节点 | **Nucleus** | 一个细胞核（一个决策 worker） |
| 复制传播的 payload | **Spore**（孢子） | 权重+playbook 打包 |
| 跨组协调者 | **Plasmodium** | 协调层（共享细胞质） |
| 休眠状态 | **Sclerotium** | 节点下线但可复活的持久化状态 |
| 自训练 | **Sporulation** | 产孢=进化 |

## 次推：Pando

**拉丁语原意就是“我蔓延”（I spread）**。这是地球上已确认的**最大单一生物体**：犹他州一片看似有 47,000 棵独立颤杨的森林，地下其实全部连着同一套根系，是**一棵树**（[Wikipedia](https://en.wikipedia.org/wiki/Pando_%28tree%29)、[NASA Earth Observatory](https://science.nasa.gov/earth/earth-observatory/saving-a-forest-of-one-151022/)）。

意象映射：地面上每棵“树”看起来独立（异构设备），地下共享一套根系统（共识协议/权重血统），个体不断从根系萌发新茎（弹性扩容），总重约 6,000 吨、可能活了 8 万年（统一智能的持久性）。"I spread" 作为 tagline 也极强——GitHub README 第一行写 `Pando: the forest that is one tree.` 就足够了。

比 Physarum 更短、更暖、更容易被英语世界记住。缺点：意象里少了“多头的怪异感”，偏“和平共生”而非“无限繁殖的野性”。命名空间方面，pando.com 是一家已经死掉的科技媒体，干扰不大。

## 为什么不是那些“听起来更强”的名字

- **Hydra**：意象完美（砍一头长两头=容错），但命名空间是灾难级的——Facebook 的 Hydra C++ 配置库、Cardano 的 Hydra L2、OWASP Hydra、ZyreApps 的 hydra 去中心化协议、ECCV 的 HYDRA 视觉 agent……你会在搜索结果第五页才被找到。如果你一定要用 Hydra 的意象，**Physarum polycephalum 的种加词 polycephalum 本身就是"多头"**——你用 Physarum 就等于用了一个更冷门、更精确、不撞车的 Hydra。
- **Medusa**：在 LLM 推理领域已被 [FasterDecoding/Medusa](https://github.com/FasterDecoding/Medusa)（推测解码框架，同一领域）和 [thustorage/Medusa](https://github.com/thustorage/Medusa)（ASPLOS'25）占据，直接撞车。
- **Ouroboros**：意象极好（自食=自训练循环），但 Cardano 区块链的共识协议就叫 Ouroboros，在“分布式共识”这个概念空间里正面相撞。
- **Tiamat**：巴比伦原初母神，生下了**十一种完全不同的怪物**（异构融合的隐喻非常好），但已有交通数据库 entur/tiamat 和 Tiamat Tech 等项目。

## 直接回答：单设备内异构拼装，今天就有生产级支持

你的直觉是对的，而且**“每个设备只能用一个算力单元”是过时假设**。Intel 平台原生提供两条现成路径（OpenVINO 官方文档，2026 版）：

| 模式 | 机制 | 适合 |
|---|---|---|
| **HETERO**（异构执行） | 把模型**按层切成多个子图**，按优先级分配给不同算力单元（如 `HETERO:GPU,CPU`，也支持 NPU、dGPU、iGPU），贪心分配 | 单模型太大或想用各单元特长 |
| **MULTI**（多设备执行） | **同一个模型**在多个算力单元上同时跑**不同请求**，按优先级调度（`MULTI:GPU.1,GPU.0`） | 吞吐扩展——我们的 fan-out 投票天然就是多并发请求，完美匹配 |

另外 **ipex-llm**（Intel 官方 LLM 库）已支持 CPU+iGPU+NPU+dGPU 全家桶，甚至在 2 张以上 Intel GPU 之间做流水线并行/张量并行（2024-06 起）。

## 但要先纠正一个硬件认知

“共享一份内存的几个对等单元”不准确，AI PC 内部其实是**两种拓扑并存**：

- **iGPU + NPU + CPU**：真·共享系统内存（iGPU/NPU 无独立显存），数据交换近乎零拷贝——但它们**共享同一条内存带宽**，这才是真正的瓶颈，三个单元同时猛跑会互相抢带宽
- **dGPU / 外接 GPU**：独立显存 + PCIe 连接，跨单元传输有真实代价

所以“拼装”的最优策略因单元而异，不是无脑全用上。

## 三个工程坑（文档明确记录的）

1. **NPU 只支持静态 shape**（动态 shape 是 preview 且受限；Qwen3-0.6B INT4 在 NPU 上还有未解的编译 bug）——好消息是 Laya 是定长 encoder（512/1024 ctx），天然 NPU 友好，但 **batch 必须 pad 到固定尺寸**
2. **ONNX Runtime 单 session 只能有一个同类 EP 实例**——iGPU+外接 GPU 在一个 ORT session 里做不到，要么双 session 要么换 OpenVINO（它原生枚举 GPU.0/GPU.1）
3. **HETERO 切分点需要实测**：官方文档直言，若子图间传输开销超过收益，异构执行“可能得不偿失”——自动贪心分配不保证最优

## 对 PandoSI 架构的关键修正

这轮调研迫使我们升级一个核心抽象：**原子资源单位从“设备（Device）”改为“算力单元（ExecutionUnit, EU）”**。一台 AI PC = 4 个 EU，由此产生三种拼装形态：

```
形态 A：单 worker + HETERO 后端     —— 一个 EU 池跑一份 Laya，层间切分
形态 B：多虚拟 stem（每 EU 一个）    —— 4 个 EU 各跑一份 Laya 副本，各自参与 quorum
                                      ★ 正好喂饱我们"共识需要异构副本"的定量需求
形态 C：混合                        —— NPU 跑高频低延迟判定，CPU 跑校准/管理，
                                      GPU 跑大模型 draft
```
